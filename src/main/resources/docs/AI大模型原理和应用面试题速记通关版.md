# 请解释⼤模型微调(Fine-tuning)的原理，并说明在什么业务场景下需要微调⽽不是直接使⽤基础模型？

微调的本质是参数⾼效迁移，不是从头训练。⼤模型已经在海量通⽤语料上学到了语⾔规律和世界知识，微调是在这个基础上，⽤特定领域的数据去调整模型参数，让它适应新任务。

1）你拿到⼀个预训练好的⼤模型，⽐如LLaMA或Qwen，它的“常识”已经很完整。但如果你要做⾦融研报⽣成，它可能写得不够专业。这时候直接prompt⼯程搞不定，因为领域术语、⾏⽂逻辑差异太⼤。

2）微调就是拿⼀批⾦融报告数据，⽤有监督的⽅式继续训练。⽐如输⼊“某公司营收增⻓ $3 0 \%$ ”，让模型输出对应的研报段落。反向传播会更新权重，让模型在该任务上表现更好。

3）关键在于，并不是所有层都要重训。现在很多做法是只微调部分参数，⽐如LoRA（Low-RankAdaptation），冻结原模型权重，只训练低秩矩阵。这样显存占⽤少，训练快，适合业务迭代。

# 需要微调的场景通常是：

输出格式/⻛格强约束，⽐如法律⽂书、医疗诊断记录

领域知识密集，基础模型没⻅过的专业术语体系

企业私有数据不能⾛API，必须本地部署并定制

如果只是简单问答、摘要⽣成，且对表达⻛格要求不⾼，那其实⽤提⽰词+RAG就够了。微调成本⾼，周期⻓，真要上得想清楚是不是⾮⽤不可。

# RAG的完整流程是怎么样的？

RAG的流程其实就三步：准备数据、查资料、⽣成答案。整个过程让⼤模型在回答前，先去“翻书”找依据。

1）数据准备阶段，先把外部知识库的⽂档切⽚，⽐如把PDF或数据库表结构说明拆成⼀段段⽂本块。接着⽤embedding模型给每⼀块转成向量，存进向量数据库，像Milvus或Pinecone这类⼯具⼲的就是这事。

2）⽤户提问时，系统不会直接扔给⼤模型。⽽是先把问题也转成向量，去向量库⾥做相似度搜索，找出最相关的⼏个⽂本块。这⼀步很关键，决定了模型能“看到”哪些背景知识。

3）最后，把这些检索到的⽂本块拼接成提⽰词，连同原问题⼀起喂给⼤模型。模型基于这些上下⽂⽣成答案，⽽不是靠记忆瞎编。这样出来的回答有据可查，幻觉少。

这个流程⾥，embedding模型和向量检索的质量直接决定效果。如果检索错了，后⾯再强的模型也搞不定。常⻅坑是⽂本分块不合理，⽐如按固定字符切，把⼀个完整概念切碎了，导致查不准。

# 什么⾃查询？为什么在RAG中需要⾃查询？

⾃查询其实是让模型⾃⼰⽣成查询条件，去检索它需要的信息。⽐如你问“苹果最新财报怎么样”，模型不会直接回答，⽽是先拆解问题，⽣成像“苹果2024年Q2营收、利润、同⽐增⻓”这样的检索关键词，再拿这些词去查⽂档。

这在RAG⾥特别关键，因为原始问题往往太笼统或包含多个维度。直接拿原问题去搜，召回的内容可能不精准。⾃查询相当于加了⼀层智能路由，把复杂问题翻译成适合检索的结构化查询语句。

1）能处理时间范围过滤，⽐如“去年销售额最⾼的产品”会被转成带时间约束的查询

2）⽀持属性筛选，“便宜的安卓⼿机”会拆成“价格低于2000元、操作系统为Android”

3）适配向量库的元数据检索，⽐如⽤ Chroma 或 Pinecone 的 where 条件过滤

代码上⼀般⽤LLM接⼀个提⽰模板：

```dart
String prompt = "根据用户问题生成检索查询语句：" + userQuestion;  
List<String> queries = lvm_generate(prompt);  
List<Document> results = vectorStore.search(quries);
```

整个流程像是给RAG装了个“理解⼤脑”，先把⼈话转化成机器能⾼效检索的指令，避免压根不经过语义解析就硬搜。

# 什么提⽰压缩？为什么在RAG中需要提⽰压缩？

提⽰压缩其实就是把RAG中过⻓的上下⽂输⼊给“瘦⾝”。你想想，⼤模型的上下⽂⻓度是有限的，⽐如32K或128K，但检索回来的⽂档⽚段⼀多，加上原始问题和模板，很容易就超了。

1）最直接的问题就是token数爆掉，请求直接被拒，压根不经过模型推理。

2）就算没超，⻓上下⽂推理成本⾼，响应慢，延迟上去⽤户体验就差了。

3）⽽且很多检索出的内容其实跟问题关系不⼤，纯属噪⾳，反⽽⼲扰⽣成质量。

所以得做提⽰压缩，把那些冗余信息、重复段落、⽆关句⼦给剔除或简化。不是简单删减，⽽是保留关键事实和语义，让输⼊更紧凑⾼效。

常⻅的做法有⼏种：

⽤⼩模型先做⼀轮重排序或摘要，⽐如⽤BGE或Coherereranker挑最相关的top-k。

在 prompt 组装时加逻辑，只保留⾼分 chunk，甚⾄对每个 chunk 做句⼦级裁剪。

也可以引⼊类似 HyDE 的思路，先⽣成假设答案再反向匹配，过滤低相关度内容。

代码上没啥复杂语法，核⼼是控制组装后的总token数：

# 伪代码⽰意

```txt
context = "\n".join([chunk["text"] for chunk in relevantChunks[:3]]) # 限制数量
prompt = f"基于以下内容回答：\n{context}\n\n问题：\{\text}{query}"
```

要不要压缩，其实看场景。如果检索精度⾼、返回少，可能不需要。但⾯对海量⽂档库，⽐如⽤在企业知识库搜寻，就得靠这招扛住⻓上下⽂压⼒。

# 什么是RAG中的分块？为什么需要分块？

RAG的上下⽂⻓度是有限的，⽐如主流模型⼀般⽀持32k或128k的token上下⽂。你塞进去的prompt越⻓，能留给检索内容的空间就越少。分块其实就是把原始⽂档切成适合模型处理的⼩段落，让每次检索和⽣成都能在上下⽂窗⼝内完成。

1）分块不是简单按段落切。如果按固定字符数切，可能把⼀句话从中间劈开，语义就断了。好的分块策略会尽量保持语义完整，⽐如⽤递归分割，先按标题切，再按段落，最后才是固定⻓度。LangChain⾥的

RecursiveCharacterTextSplitter 就是这么⼲的。

2）块太⼩，信息不全，模型容易“只⻅树⽊不⻅森林”；块太⼤，⼜挤占上下⽂，影响其他prompt内容。⼀般来说，512到1024个token是⽐较常⻅的块⼤⼩，具体得看你的数据和模型。

3）有些场景还得考虑跨块关联。⽐如⼀个技术⽅案分布在三个块⾥，单靠⼀个块检索出来，模型也拼不全逻辑。这时候就得靠后续的查询扩展或多步检索来补救。

代码上⼤概⻓这样：

from langchain.text_splitter import RecursiveCharacterTextSplitter 

splitter $=$ RecursiveCharacterTextSplitter( chunk_size=512, chunk_overlap $\coloneqq$ 50, separators $\coloneqq$ ["\\n\\n", "\n", "。", " ", "", ])   
docs $=$ splitter.split_text(large_document) 

要不要分块，其实取决于你的数据形态和检索⽬标。像PDF、⻓⽹⻚这种肯定要分，但如果是短问答对，可能直接喂进去就⾏。

# 在RAG中，常⻅的分块策略有哪些？分别有什么区别？

分块策略直接影响检索效果，选不好后⾯全⽩搭。关键得看⽂本的语义连贯性和上下⽂依赖。

# 1）固定⼤⼩分块

按字符或token数硬切，⽐如每512个token切⼀块。简单粗暴，适合结构规整的⽂档。但容易把⼀句话从中间劈开，语义被撕裂，检索回来的⽚段可能压根不经过原意。像PDF或⽹⻚正⽂这种连贯性不强的还⾏，但技术⽂档、论⽂就搞不定。

# 2）基于段落或标题分割

利⽤⾃然断点，⽐如⼀级/⼆级标题之间、空⾏处分割。能保留完整语义单元，适合 Markdown、Word 这类有结构的⽂档。问题在于块⼤⼩不均匀，有的标题下内容贼⻓，检索时信息密度太低。

# 3）滑动窗⼝重叠分块

在固定⼤⼩基础上，让相邻块有部分重叠，⽐如每次滑动512，重叠 $12 8 _ { \circ }$ 。这样能缓解语义断裂，关键信息⼤概率出现在多个块⾥。但会增加索引量和检索耗时，重复内容多，存储成本翻倍也不稀奇。

# 4）语义感知分块（如 RecursiveCharacterTextSplitter）

先按标点切，再按⻓度合并，尽量保证句⼦完整。LangChain⾥默认⽤这个，实际项⽬中表现最稳。更进⼀步可以⽤嵌⼊模型做句⼦相似度判断，在语义边界处分割，不过延迟⾼，⼀般⽤在对精度要求极⾼的场景。

选哪种？短平快任务⽤滑动窗⼝ $| + \rrangle$ 固定⼤⼩，追求效果上语义分块，有明确结构就优先标题分割。

# 在 RAG 中的 Embedding 嵌⼊是什么？

Embedding在RAG⾥⼲的事，就是把⽂本转成机器能算的“数字向量”。你给它⼀句话、⼀段⽂档，它就输出⼀个⻓⻓的浮点数数组，这个数组得能保留原⽂的语义信息。

⽐如你搜“怎么修⾃⾏⻋”，系统其实不是在关键词匹配，⽽是先把这句话做个Embedding变成向量，再去向量空间⾥找和它最接近的那些⽂档⽚段。像⽤百度搜索那种关键词匹配早就跟不上了，现在都靠这种语义相似度来找答案。

1）这活⼀般由预训练模型来⼲，⽐如BERT、Sentence-BERT（SBERT），或者专⻔做检索的bge模型。它们会把不同⻓度的⽂本压到固定维度的向量⾥，常⻅的是768或1024维。

2）RAG流程中，Embedding主要⽤于两个地⽅：⼀是离线把知识库⽂档切⽚后全部向量化存进向量数据库，⽐如⽤FAISS、Milvus 或 Pinecone；⼆是线上⽤户⼀提问，⽴刻转成向量去库⾥查 top-k 最相似的 chunk。

3）效果好不好，关键看Embedding是否真能把相近意思的⽂本“拍”到向量空间⾥挨得近。如果“如何重启路由器”和“拔电源再插上”这两个句⼦向量距离很近，那说明嵌⼊质量⾼。

代码上基本就是调个model.encode(text)就完事，但背后模型选型、是否微调、向量索引构建⽅式都会影响最终召回率。

# 在 RAG 中，你知道有哪些 Embedding Model 嵌⼊模型？

Embedding模型在RAG⾥头其实就⼲⼀件事：把⽂本转成向量，让检索系统能算相似度。选对模型直接影响召回质量。

主流的通⽤嵌⼊模型有Sentence-BERT（SBERT），它在BERT基础上加了个池化层，专⻔优化句⼦级表⽰。⽐如你⽤ paraphrase-MiniLM-L6-v2 ，⼩模型快，适合轻量场景。

进阶⼀点的是Cohere提供的multilingual-2和command-r系列，尤其是多语⾔⽀持好，在跨语⾔检索⾥表现稳。Cohere的API易⽤，但得⾛⽹络请求。

还有OpenAI的text-embedding-ada-002，虽然不开放本地部署，但在英⽂任务上精度⾼，适合不想调参直接上⽣产的场景。

开源界现在⽤得猛的是BGE（来⾃智源研究院），⽐如bge-small-zh-v1.5，中⽂场景下效果拉满，本地跑起来也顺。它通过“查询-⽂档”对增强训练，特别适配RAG的检索偏好。

别忘了还有JinaAI推的jina-embeddings-v2，⽀持8192token⻓度，⻓⽂本处理有优势，⽽且许可友好，能商⽤。

选模型得看三点：语⾔是否匹配、延迟能不能压住、有没有⻓⽂本需求。别⼀上来就⽤⼤模型，⼩模型蒸馏过的在$9 0 \%$ 场景都够⽤。

# 什么是MCP协议，它在AI⼤模型系统中的作⽤是什么？

MCP协议并不是⼀个在AI⼤模型领域⼴泛通⽤的标准协议，⽬前也没有权威⽂献或主流框架将其定义为类似HTTP、gRPC那样的基础通信协议。它更可能是指特定⼚商或系统内部定义的模型控制平⾯（ModelControlPlane）协议，⽤于协调⼤模型服务中的调度、分发与⽣命周期管理。

在典型的推理服务平台⽐如阿⾥云百炼、vLLM或TritonInferenceServer中，这类“控制协议”主要⼲三件事：

1）接收推理请求并做路由决策，⽐如该发给哪个模型实例、是否需要扩缩容

2）管理模型加载、卸载、版本切换，确保GPU资源⾼效利⽤

3）收集监控指标，配合实现弹性伸缩和故障转移

你可以把它理解成K8s⾥的kubelet和APIServer之间的通信逻辑，只不过⾯向的是模型实例⽽不是容器。真正的请求处理⸺也就是数据平⾯（Data Plane）⸺还是靠 gRPC 或 REST 承载实际的 token 流量，⽽ MCP 这类控制指令通常⾛独⽴通道，频率低但关键性⾼。

```groovy
// 伪代码示意：控制平面接收加载模型指令  
void onReceiveLoadModel(StringIFESTId, String version) {  
    ModelInstance instance = createOrReuseInstance(modelId);  
    instance.loadFromStorage(); //可能涉及 mmap、量化加载等优化  
    registerToRouter.instance); //注册到流量路由器  
}
```

要不要⽤这类协议，取决于系统规模。⼩场景直接API调⽤就够了，上了百个模型实例后，就得靠统⼀控制平⾯来“扛住”运维复杂度了。

# MCP架构包含哪些核⼼组件？

MCP架构这个词在主流技术领域没有统⼀标准定义，更常⻅的类似缩写是MCP（Model-View-Presenter）属于UI架构模式，常⽤于客户端开发。但如果你指的是服务端或中间件场景下的某种定制架构，可能是特定团队对消息驱动、控制平⾯分离类系统的简称。

不过从实际系统设计⻆度看，如果把 MCP 理解为 Message-Driven Control Plane 这类架构，它的核⼼组件⼀般包含三个部分：

# 1）消息中枢

负责路由和分发指令，⽐如⽤Kafka或RocketMQ做命令总线，所有控制指令通过Topic⼴播。消费者按需订阅，实现解耦。这种设计在微服务治理中很常⻅，像Nacos配置变更就是靠⻓轮询 $^ +$ 消息通知双机制推到客户端。

# 2）控制单元

接收消息后执⾏具体逻辑，⽐如修改本地状态、调⽤外部接⼝、触发任务调度。它不直接暴露HTTP接⼝，⽽是被动响应事件。Spring Cloud Stream 的 $@$ StreamListener 就是典型写法，压根不经过 Web 层。

# 3）状态反馈器

反向上报执⾏结果，形成闭环。通常往⼀个集中式存储写状态，⽐如把节点健康度打到Redis，或者把执⾏⽇志发到Elasticsearch。ZooKeeper 临时节点也⼲这事，会话⼀断⾃动清理状态。

# MCP协议⽀持哪两种模式？

MCP（ModelContextProtocol）⽬前主要⽀持两种交互模式，对应不同的上下⽂处理⽅式。

# 1）请求-响应模式

这是最常⽤的模式，客户端发送⼀个请求，携带特定上下⽂，服务端完全基于该上下⽂⽣成响应，交互结束。整个过程类似HTTP的调⽤模型，适合⼀次性任务，⽐如让⼤模型总结⼀段⽂本、翻译⼀句话。这种模式下，上下⽂只在当前请求中⽣效，不会保留。

# 2）会话模式

系统会维护⼀个持续的上下⽂会话状态，客户端可以连续发送多条消息，每条都基于之前的对话历史进⾏理解与回应。典型场景是聊天机器⼈、AI助⼿这类需要记忆上下⽂的产品，⽐如使⽤MCP协议对接LLM构建客服系统时，⽤户前⼏轮提到的信息要能在后续对话中被引⽤。

会话模式的关键在于服务端需要管理Session状态，可能结合UUID或token来标识不同⽤户的上下⽂隔离。⽽请求-响应模式⽆状态，更容易⽔平扩展。

要不要⽤会话模式，得看业务是否需要“记住”前⾯的内容。如果只是做离散任务，⽐如内容审核、关键词提取，压根不需要维持状态，⽤第⼀种就够了。

# MCP 与 Function Calling 的区别是什么？

MCP 和 Function Calling 看似都在让模型“调⽤功能”，但它们的定位和机制完全不同。

MCP其实是⼀种协议，更准确地说是ModelContextProtocol，它定义了外部系统如何向⼤模型提供上下⽂、⼯具描述以及如何接收模型的结构化输出。它不绑定具体实现，强调的是模型与环境之间的标准化交互⽅式。你可以把它理解成⼀个通⽤的“插件通信规范”，像GitHubCopilotExtensions就基于这类思想构建扩展能⼒。

⽽FunctionCalling是具体的能⼒，指的是⼤模型能根据输⼊决定是否调⽤某个预定义函数，并⽣成符合schema的参数。主流闭源模型如GPT-4都⽀持这个特性，它是实现Agent⾏为的基础组件之⼀。⽐如你⽤LangChain写个天⽓查询，模型会判断⽤户意图后返回 {"name": "get_weather", "arguments": {"city": "Beijing"}} 这样的结构。

关键区别在于：FunctionCalling是单⼀模型对外暴露的能⼒接⼝，MCP则是多个系统间协作的协议框架，⽀持更复杂的双向交互和资源共享。

# MCP的⼯作流程是什么？

MCP 其实是 Model Context Protocol 的缩写，它不是传统中间件或 Java 领域的标准组件，⽽是在 AI Agent 架构中⽤来规范⼤模型与外部⼯具、数据源之间交互的协议。它的核⼼作⽤是让模型能安全、可控地访问运⾏时上下⽂。

整个流程从⽤户发起请求开始。Agent接收到输⼊后，会先做⼀次意图解析，判断是否需要调⽤⼯具。如果需要，就会构造⼀个符合MCP格式的请求包，⾥⾯包含动作类型、参数和上下⽂元信息。

接下来这个请求会被转发给对应的⼯具适配器。⽐如你要查数据库，就会⾛SQL⼯具链；要发HTTP请求，就交给API客户端处理。执⾏结果原路返回，由MCP解析器把原始响应转成模型能理解的⾃然语⾔⽚段。

1）请求触发：⽤户输⼊进⼊Agent循环

2）决策判断：Controller判断是否需外部调⽤

3）协议封装：按MCP标准⽣成toolcall消息

4）⼯具执⾏：Adapter调⽤具体服务并获取结果

5）上下⽂注⼊：将结果以结构化⽅式回填到prompt上下⽂

这种设计的好处是解耦了模型逻辑和外部系统。像LangChain或SemanticKernel这类框架，底层其实就是靠类似MCP的机制在做调度。你不需要改模型代码，只要注册新⼯具就能扩展能⼒。

# 在 Spring AI 框架中如何集成 MCP？

SpringAI框架本⾝是Spring⽣态中⽤于接⼊⼤模型服务的抽象层，它的设计⽬标是让Java应⽤能统⼀⽅式调⽤不同AI平台的能⼒。MCP（ModelContextProtocol）是⼀种⽤于在客户端与模型服务之间传递上下⽂信息的协议，常⻅于某些私有化部署或定制化推理平台。

要把MCP集成进SpringAI，关键在于⾃定义客户端适配器。SpringAI⽀持扩展 ChatClient 接⼝，你可以基于RestClient 或 WebClient 实现⼀个专⽤于与⽀持MCP协议的服务通信的客户端。

1）你需要先定义请求结构体，匹配MCP规范⾥的字段，⽐如 context , prompt , model 等。2）通过@RegisterAiClient 注解注册你的实现，或者⼿动配置为 Bean 。 3）在调⽤时注⼊ ChatClient ，框架会⾃动路由到你的MCP适配器。

```java
@Bean

} 
```

实际请求中，header或payload⾥要带上MCP要求的元数据，⽐如会话ID、租户上下⽂等。这类脏活累活⼀般封装在拦截器⾥处理。

如果使⽤ Spring AI $0 . 8 . 0 +$ 版本，已经⽀持SPI扩展机制，可以更⼲净地插拔协议实现。不过⽬前主流⼚商如通义千问、百川都不⾛MCP，它更多出现在内部统⼀推理⽹关场景，⽐如阿⾥云灵积的部分私有实例。

# MCP协议安全性设计包含哪些层⾯？

MCP协议本⾝并不是⼀个⼴泛标准化的通⽤协议，更多是特定系统或平台内部定义的通信规范。讨论其安全性设计，得从典型中间件通信协议的防护思路⼊⼿，⼀般会覆盖这⼏个层⾯。

传输安全靠TLS/SSL加密链路，防⽌数据被窃听或篡改，这是基础操作。⾝份认证通常⾛双向证书、APIKey或OAuth令牌，确保连接双⽅都是合法⻆⾊。访问控制会在协议层嵌⼊权限信息，⽐如Kafka的ACL机制就绑在请求头上，决定谁能读写哪个topic。

数据层⾯要防敏感信息裸奔，可以在payload内部做字段级加密，像⽀付类消息⾥的卡号，别指望⽹络层全兜住。审计和⽇志也得跟上，关键操作记录请求来源、时间、动作，出事能追溯。重放攻击靠nonce或时间戳窗⼝来防，每个请求带唯⼀序列号，服务端做校验去重。

其实很多开源框架⽐如gRPC或Dubbo，都把这套模式揉进了⾃⼰的扩展点⾥。MCP如果是⾃研协议，这些环节⼀个都不能少，否则⾼压环境下容易被钻空⼦。

# 如何将已有的应⽤转换成MCP服务？

MCP本质上是⼀套⾯向云原⽣的模块化编程模型，核⼼是把传统应⽤拆解成可独⽴部署、按需加载的微内核 $^ +$ 插件结构。你不需要重写整个系统，关键是识别出哪些模块具备“可插拔”特征。

⼀般适合改造的模块是那些业务边界清晰、依赖收敛、有明确接⼝定义的部分。⽐如你在⽤SpringBoot做⽹关，⾥⾯的鉴权、限流、⽇志收集这些功能就可以拆成MCP插件。它们共⽤⼀套上下⽂，但彼此不耦合。

改造第⼀步是引⼊MCP运⾏时容器，⽐如基于Jigsaw模块系统或⾃研ClassLoader隔离机制。然后把原有功能打成jar包，配上 module.json 或注解声明⼊⼝类和依赖关系。启动时容器会按拓扑顺序加载并激活。

代码上最简单的做法是在原项⽬加⼀个启动器：

@McpModule(name $=$ "auth-plugin",version $=$ "1.0")   
public class AuthPlugin implements ModuleLifecycle { public void onStart(Context ctx){ ctx.registerFilter(new AuthFilter()); }   
} 

注意类加载器隔离，避免第三⽅库冲突。像Apollo、Nacos这类配置中⼼的客户端通常要下沉到宿主，插件通过统⼀API获取配置。

常⻅翻⻋点是静态变量共享和线程池滥⽤。不同插件如果都new⾃⼰的ThreadPoolExecutor，很容易把机器打爆。建议统⼀⽤宿主提供的执⾏器。

![image](https://cdn-mineru.openxlab.org.cn/result/2026-04-10/a4546dd9-d3cc-4d94-90fb-a52fb3050fc3/e95c90003e6c3c4aa0a0bf26f7af81a1db25966b9876eddad6d9a8eef709ab05.jpg)


这种架构在阿⾥内部的Sentinel控制台、AntDesignPro后台都有落地，主要是为了⽀撑多租户定制化需求。⼩团队⽤的话，得评估好复杂度收益⽐，别为了架构⽽架构。

⼤模型微调是在预训练好的模型基础上，⽤特定领域的数据继续训练，让它适应具体任务。⽐如你有个通⽤语⾔模型，想让它擅⻓写法律⽂书，就拿⼀堆法律⽂本去微调它。

1）预训练是打基础，模型在海量⽆标注数据上学习语⾔规律，⽬标是理解“什么是语⾔”。这个阶段通常要⽤上千张GPU卡跑⼏周，参数量动不动上百亿。

2）微调是定向优化，⽤的是⼩规模、有标注的领域数据，⽐如客服对话、医疗报告。训练轮次少，计算资源消耗低，⼀般⼏张GPU就能搞定。它的⽬标不是从零学语⾔，⽽是调整已有知识去解决“某个具体问题”。

3）两者的区别不在代码实现，⽽在数据和⽬标。预训练像通识教育，什么都学；微调像职业培训，专精⼀项。Hugging Face 上很多 bert-base-chinese 是预训练模型，⽽ bert-wwm-ext 就是在此基础上做了额外微调的版本。

微调压根不重新训练整个⽹络，只是在原有权重上做⼩幅更新。如果任务差异太⼤，⽐如从⽂本⽣成跳到图像识别，那微调就搞不定了，得换架构重来。

# 常⻅的微调任务有哪些？

微调任务其实就是在预训练模型基础上，针对特定场景做适配。最常⻅的⼏种类型，基本覆盖了⼤部分NLP需求。

# 1）⽂本分类

把句⼦或段落分到预定义类别⾥。⽐如情感分析判断评论是正⾯还是负⾯，⽤BERT接⼀个分类头就⾏。

// 伪代码⽰意

```txt
model = BERT.from_pretrained("bert-base-uncased")
classifier = nn.Linear(768, num_labels) // 接在最后一层向量上
```

# 2）命名实体识别（NER）

找出⽂本⾥的实体，像⼈名、地名、组织名。⼀般在每个token上做序列标注，CRF层常⽤来优化标签间转移逻辑。

# 3）问答任务（QA）

最典型的是SQuAD这类抽取式问答。模型要从给定段落⾥标出答案的起⽌位置。输⼊是“问题 $\vdots +$ 段落”，输出两个指针。

# 4）⽂本⽣成

⽐如摘要⽣成、翻译。⽤T5或BART这类seq2seq模型，输⼊原⽂，输出压缩后的摘要。训练时⽤交叉熵算loss。

# 5）句⼦对关系判断

判断两句话是什么关系。⽐如⾃然语⾔推理（MNLI），看第⼆句是⽀持、⽭盾还是中⽴于第⼀句。STS任务则是算语义相似度。

这些任务的数据格式和输出头不⼀样，但训练⽅式都差不多：冻结部分底层参数，放开顶层微调，学习率通常设得⽐较⼩，3e-5到5e-5就够了。数据量⼀般⼏千到⼏万条就能⻅效，迁移学习在这⾥真能省下⼤量训练成本。

# 常⻅的微调⽅法有哪些？

微调本质上是拿预训练模型在特定任务上做⼆次训练，让模型更适配具体场景。常⻅的⽅法选择得看数据量、算⼒和任务复杂度。

1）全量微调就是把整个模型的参数都放开训练。效果通常最好，但显存消耗⼤，8张A100都不⼀定扛住Llama27B的全量微调。适合数据质量⾼、预算充⾜的场景。

2）LoRA（低秩⾃适应）现在成了主流⽅案。它冻结原模型权重，在旁边加个⼩的低秩矩阵做增量，训练时只更新这部分。显存能省下 $7 0 \%$ ，训练速度也快，Hugging Face 上⼤部分开源微调项⽬都在⽤。

# LoRA 核⼼思想：A 下降维度，B 升维，中间做低秩分解

lora_weights $=$ (x @ A) @ B 

output $=$ original_output $^ +$ lora_weights 

3）Adapter⽅法是在Transformer层之间插⼊⼩的神经⽹络模块，训练时固定主⼲，只调这些⼩模块。结构改动⽐LoRA⼤，但现在⽤得少⼀些。

4）P-Tuning 和 Prompt Tuning 属于提⽰微调，不改模型本⾝，⽽是学⼀组虚拟 token 的 embedding。适合少样本场景，但效果波动⼤，对初始化敏感。

选哪个得权衡。数据多、资源⾜，可以试全量微调；⼤多数情况下，LoRA是性价⽐之选，像Qwen、ChatGLM的社区微调基本都靠它打底。

# 什么是护栏技术？

护栏技术本质是⼀种在系统运⾏时动态控制流量、防⽌雪崩的保护机制。它不追求彻底解决问题，⽽是快速⽌损，让系统能继续对外提供部分服务。

1）核⼼思路是“宁可限流，不可拖垮”。⽐如⼀个电商系统的下单接⼝突然变慢，⼤量请求堆积，数据库连接被打满，这时候如果不加⼲预，整个应⽤可能直接宕机。护栏技术就是在这个临界点介⼊，把超出处理能⼒的请求直接拒绝或降级。

2）常⻅的实现⽅式有熔断、限流、降级。熔断像电路保险丝，当错误率超过 $5 0 \%$ 就直接切断请求，避免连锁故障；限流控制每秒最多放⾏1000个请求，多余的就地拦截；降级则是返回兜底数据，⽐如商品详情⻚的推荐模块挂了，就直接返回空列表，保证主流程可⽤。

3）实际项⽬⾥，Sentinel和Hystrix都是典型的护栏⼯具。拿Sentinel来说，你可以给某个接⼝配置QPS超过50就⾃动限流，规则可以实时推送，不⽤重启服务。

// 定义资源

SphU.entry("getOrder") 

// 业务逻辑

这种机制特别适合⽤在⾼并发场景，⽐如秒杀系统。你不可能靠堆机器扛住所有流量，得靠这些“安全策略”来兜底。真正的稳定性不是不出问题，⽽是出问题时系统还能活着。

# 什么是 GPTCache？

GPTCache是⼀个专为⼤模型应⽤设计的语义缓存中间件，⽬标是把重复或语义相近的请求直接拦截下来，减少对⼤模型API的调⽤次数，从⽽降成本、提响应速度。

它的核⼼思路不是简单地做字符串匹配，⽽是通过向量相似度来判断新来的请求和历史请求是否“意思差不多”。⽐如⽤户问“今天天⽓怎么样”和“现在外⾯晴吗”，⽂字不同但意图接近，GPTCache就可能命中缓存。

整个流程⼀般是这样：

1）⽤户请求进来，先被转换成 embedding 向量

2）在向量数据库⾥搜最近似的⼏个结果

3）如果相似度超过阈值，就返回缓存⾥的答案；否则⾛正常链路调⼤模型，并把新的question-answer存进缓存

![image](https://cdn-mineru.openxlab.org.cn/result/2026-04-10/a4546dd9-d3cc-4d94-90fb-a52fb3050fc3/7730342c3c0e894bf111904ec667f5520910dafd887ae275f61d8a0e78997446.jpg)


它适合⽤在⾼频问答、客服机器⼈、RAG 系统这类场景，尤其是请求重复率⾼、对延迟敏感的应⽤。像 LangChain、LlamaIndex 这些框架都能集成 GPTCache。

不过要注意，embedding模型的选择和距离计算⽅式会直接影响命中精度，太松容易误中，太严⼜起不到缓存作⽤。⼀般建议搭配Milvus、Pinecone或Chroma做向量存储，性能和扩展性更稳。

# 什么是 GPT Structured Outputs？

GPTStructuredOutputs是⼀种让⼤模型输出结构化数据的能⼒，⽐如JSON格式的结果，⽽不是⾃由⽂本。这在需要程序直接解析模型输出的场景⾥特别有⽤。

你告诉模型你想要的schema，它就会按这个格式返回数据。这样⼀来，前端或后端代码就能直接消费输出，不⽤再写⼀堆正则或逻辑去提取信息。

⽐如你在调⽤ GPT 时启⽤ response_format 参数，并指定为 JSON Schema，模型就会严格按字段输出。OpenAI从 2023 年底开始⽀持这个功能，适⽤于像 gpt-3.5-turbo 和 gpt-4 这样的模型。

```json
{ "name": "Alice", "age": 30, "city": "Beijing" } 
```

这种机制适合做配置⽣成、表单填充、API数据抽取等任务。和以前“靠运⽓”解析⽂本不同，现在结果可预测、可验证。

不过得注意，模型不会⾃动知道什么时候该输出结构，必须显式设置参数，否则还是⾛⾃由⽣成。另外复杂schema可能增加token消耗，设计时要权衡清晰度与成本。

如果原题解中的某句话使⽤了超链接，不要对这句话做任何改动。

# 什么是 LangChain？

LangChain是个帮助开发者快速搭建应⽤的框架，重点是让⼤模型和外部系统打通。你不⽤从零写prompt调⽤、上下⽂管理、⼯具调⽤这些重复代码，它都给你封装好了。

它的核⼼能⼒之⼀是链式调⽤，你可以把多个步骤串起来，⽐如先查数据库，再让⼤模型总结，最后发个通知。每个环节它都抽象成组件，像积⽊⼀样拼接。

另⼀个关键点是跟外部数据对接。⽐如你要做个客服机器⼈，不能光靠模型内置知识，得让它查你的产品⽂档。

LangChain提供了和向量数据库集成的能⼒，像和Pinecone、Weaviate对接，做检索增强⽣成（RAG），这样回答就有据可依。

它还⽀持Agent模式，就是让模型⾃⼰决定下⼀步⼲什么。⽐如⽤户问“昨天销售额最⾼的订单是谁”，模型可以⾃⼰判断要先查订单表，再查客户信息，然后组织语⾔回复。背后其实是模型输出特定格式指令，框架负责解析并执⾏。

代码上它很简洁，⼏⾏就能定义⼀个链：

```python
from langchain.chains import LLMChain  
chain = LLMChain(llm=llm, prompt=prompt)  
response = chain.run("中国的首都是哪里？")
```

适合做需要动态输⼊、多步推理、结合私有数据的场景，⽐如智能客服、数据分析助⼿。但如果你只是简单问答，可能显得重了。

# 什么是 LangGraph ？

LangGraph是基于LangChain构建的有状态的多智能体协作框架。它把多个AIAgent的交互过程建模成“图”（Graph），每个节点是⼀个执⾏单元，边代表控制流或数据流向。

这种图结构让你能清晰定义复杂的agent协作逻辑。⽐如⼀个节点是⽤户输⼊处理，另⼀个是⼯具调⽤，第三个是决策判断，通过边连接它们的执⾏顺序。整个流程的状态被显式维护，后续节点可以访问前⾯所有步骤的数据。

它特别适合做需要反复来回交互的任务。像客服系统⾥，⼀个agent处理意图识别，发现信息不全就转给追问agent，补全后再交给业务办理agent。这种循环、条件跳转、状态保持的场景，传统流⽔线搞不定，⽽LangGraph能扛住。

代码上其实就是定义⼀堆节点函数，然后⽤ add_node 和 add_edge 把它们串起来，最后编译成⼀个可执⾏的graph。调试时还能看到每⼀步的状态快照，排查问题⽅便多了。

举个实际场景：⽤LangGraph搭⼀个多轮审批流，结合Human-in-the-loop，在关键决策点暂停等待⼈⼯确认，确认后继续往下⾛，整个过程可追溯。

这个模型让复杂agent⼯作流变得结构化，⽽不是⼀堆混乱的回调和全局变量。

# LangGraph 编排的原理是什么？

LangGraph的本质是把⼤模型的执⾏过程变成⼀个有向图，每个节点是⼀个动作或决策点，边代表执⾏路径。你给它⼀个输⼊，它就从起点开始，按图的结构⼀步步⾛，⾛到哪、下⼀步⼲啥，由当前节点的逻辑决定。

1）节点可以是调⽤⼤模型、执⾏⼯具、做条件判断，甚⾄是⼈⼯审核这种阻塞操作。⽐如在客服机器⼈⾥，⼀个节点可能是“识别⽤户意图”，下⼀个节点根据意图跳转到“查订单”或者“投诉处理”。

2）每⼀步的状态都通过⼀个共享的state对象传递，这个state是可变的，后续节点能读也能改。这就让整个流程有了上下⽂记忆，不像普通函数调⽤那样孤⽴。

3）控制流靠的是 conditional edges，也就是条件边。你可以写个函数判断 state ⾥的字段，返回下⼀个节点的名字。⽐如判断“是否需要⼈⼯介⼊”，返回 "human_in_the_loop" 或 "continue_automated"。

代码上其实就是定义节点函数和边规则：

```python
graph.add_node("generate", generate)  
graph.add有条件的Edges("generate", route_generate_result)
```

整个执⾏过程是同步推进的，但每步之间可以暂停、恢复，适合⻓周期任务。像AutoGen、CrewAI这些框架底层也⽤了类似思路，只是LangGraph更灵活，⽀持复杂DAG。

# LangChain 和 LangGraph 有什么区别？

LangChain是个⼯具箱，帮你快速搭起和⼤模型交互的流⽔线。你拿它做点简单的链式调⽤，⽐如⽂档加载、切分、检索再喂给LLM⽣成答案，整个流程像⼀条直线，串⼏个组件就跑起来。适合做些原型或者轻量级应⽤，⽐如基于⽂档问答的⼩⼯具。

LangGraph就不⼀样了，它是专⻔搞有状态、多步骤、带循环的复杂Agent流程的。你可以把它看成是LangChain的“升级控制器”。它⽤有向图来建模流程，节点是动作，边是转移逻辑，能表达“失败重试”、“条件跳转”、“⼈类介⼊”这种复杂控制流。⽐如你做个多智能体协作系统，A⼲完活交给B，B觉得不⾏⼜回滚给A，这种环状依赖，LangChain 原⽣链式结构压根不经过，但 LangGraph 天⽣⽀持。

打个⽐⽅：LangChain是条流⽔线，⼯件从头⾛到尾；LangGraph是个调度⽹络，能根据情况动态派单、回流、并⾏处理。

代码上，LangGraph核⼼是 StateGraph ，你定义⼀个共享状态，每个节点函数读写这个状态，然后通过条件边决定下⼀步去哪：

```python
from langgraph.graph import StateGraph  
graph = StateGraph(State)  
graph.add_node("draft", draft_node)  
graph.add_node("review", review_node)  
graph.add有条件的Edges("review", should_rework)  
graph.add_edge("draft", "review")
```

这种模式在做AutoGen、MetaGPT那类复杂Agent编排时特别扛住，脏活累活都让它揽了。

# 什么是Manus？说说你对它的了解

Manus不是Java或中间件领域的技术组件，它其实是⼀个由上海AI实验室推出的开源⼤模型智能体框架。你可以把它理解成⼀个能让⼤语⾔模型“动起来”的⼯具链，让模型不仅能回答问题，还能执⾏任务。

它最⼤的特点是⽀持⾃主规划与⼯具调⽤。⽐如给它⼀个复杂⽬标，像“分析某⽀股票的历史⾛势并⽣成报告”，Manus能⾃⼰拆解任务：先搜索实时股价，再调⽤Python分析数据，最后⽣成可视化图表和⽂字总结。背后依赖的是强化学习和思维链（CoT）的结合。

典型架构包含⼏个核⼼模块：任务分解器、⼯具路由、记忆存储和反馈循环。它不像传统微服务那样靠RPC通信，⽽是通过语义驱动动作选择。

# ReAct是什么？说说它的原理

ReAct是⼀种让⼤模型在做推理时，既能思考（Reasoning）⼜能⾏动（Action）的框架。它的核⼼不是单纯输出答案，⽽是通过交错的“想⼀步、做⼀步”来完成复杂任务。

模型在处理问题时，会先⽣成⼀段思考内容，⽐如分析当前情况、设定下⼀步⽬标，然后决定⼀个具体操作，⽐如调⽤⼯具、查数据库或搜索⽹⻚。这个动作执⾏后拿到结果，再喂回模型继续下⼀轮思考，直到得出最终答案。

这种模式特别适合需要外部交互的任务，像客服机器⼈查订单状态，或者智能助⼿执⾏多步操作。相⽐纯推理，它能获取实时数据；相⽐纯指令驱动，它多了规划和反思能⼒。

举个例⼦，你要查天⽓并决定是否带伞，ReAct会先想“我需要知道当前位置的天⽓”，然后触发“调⽤天⽓API”动作，拿到结果后再判断“预报有⾬，建议带伞”。

整个过程就像⼈在解决问题时的习惯：思考 ⾏动 观察 再思考。语⾔模型不再只是被动回答，⽽是主动推进任务。

LLMAgent的基本架构有哪些组成部分？

LLMAgent不是简单地调⽤⼤模型，⽽是⼀个能感知环境、做出决策并执⾏动作的智能体。它的结构更像是⼀个闭环控制系统。

# 1）感知模块（Perception）

负责接收外部输⼊，⽐如⽤户指令、环境状态或历史交互记录。这部分会把原始信息转换成模型可理解的格式，通常就是拼接到 prompt ⾥。

# 2）规划模块（Planning）

这是 Agent 的“⼤脑”，⼜可以拆成两块：

推理（Reasoning）：让模型对当前问题进⾏多步思考，⽐如使⽤思维链（Chain-of-Thought），先想“我该怎么做”，再决定下⼀步。

任务分解（TaskDecomposition）：复杂任务会被拆成多个⼦任务，按序或并⾏处理，像LangChain中的Plan-and-Execute 就是典型实现。

# 3）记忆模块（Memory）

维持短期和⻓期上下⽂。短期记忆⼀般是当前对话的token上下⽂窗⼝，受限于模型⻓度；⻓期记忆则依赖向量数据库，⽐如⽤Milvus或Chroma存储历史经验，需要时检索召回。

# 4）⼯具调⽤与执⾏（Tool Use & Action）

Agent能主动调⽤外部⼯具，⽐如查天⽓、执⾏代码、操作数据库。主流做法是通过函数调⽤（FunctionCalling）机制，让模型输出结构化JSON去触发API，例如在OpenAI的接⼝中定义tools列表。

整个流程⾛下来，其实就是⼀个“观察 思考 决策 ⾏动 观察”的循环。

# LLMAgent常⻅功能有哪些？

LLMAgent不是简单的问答机器⼈，它得能感知环境、做规划、调⼯具、持续执⾏直到⽬标完成。你可以把它看成⼀个“AI执⾏官”，⾃⼰拆任务、调接⼝、纠错重试。

# 1）规划与⽬标分解

Agent接到“分析竞品并写报告”这种⼤任务，不会⼀⼝吞，⽽是拆成查资料、读PDF、对⽐数据、⽣成初稿、润⾊⼏步。像 LangChain 的 PlanAndExecute 就是⼲这个的典型模式。

# 2）⼯具调⽤（Function Calling）

它得知道什么时候该让别⼈⼲活。⽐如查实时股价，直接调AlphaVantageAPI；订会议室就⾛钉钉或⻜书开放平台。模型输出结构化指令，框架负责转成真实调⽤。

# 3）记忆能⼒

短时记忆靠上下⽂窗⼝存对话历史，⻓时记忆就得接外部存储。⽐如⽤Chroma或Milvus存过往决策记录，下次遇到类似任务能参考。

# 4）⾃主执⾏与反思

有些Agent能⾃⼰决定下⼀步。AutoGPT是个例⼦，但它容易陷⼊循环。更稳的做法是ReAct模式：每步“思考-⾏动-观察”，像⼈⼀样边做边看结果。

# 5）多 Agent 协作（进阶）

复杂场景下会分⼯。⽐如⼀个当产品经理提需求，⼀个当⼯程师写代码，⼀个当测试员验证，通过内部通信达成⽬标。MetaGPT就模拟了这种⻆⾊分⼯。

# 市⾯上有哪些主流的LLMAgent框架？各⾃的特点是什么？

主流的 LLM Agent 框架这⼏年发展很快，基本都围绕“如何让⼤模型更可靠地完成复杂任务”在设计。

1）LangChain是最早⽕起来的框架，⽣态最全，⽀持的数据源、⼯具、模型最多。它的优势在于灵活，像搭积⽊⼀样组合组件，适合做原型验证。但灵活性带来的问题是代码结构容易混乱，调试困难，⽣产环境需要较强的⼯程能⼒压得住。

2）LlamaIndex起家是为了解决⼤模型对接私有数据的问题，核⼼强项是检索增强⽣成（RAG）。它对⽂档切分、索引构建、查询优化做了很多深度优化，⽐如⽀持分层索引、动态获取上下⽂。如果你的Agent主要靠读⽂档回答问题，⽐如⽤在企业知识库场景，LlamaIndex通常⽐LangChain更⾼效。

3）AutoGPT名⽓很⼤，主打“⾃主任务分解”，能⾃⼰拆⽬标、调⼯具、循环执⾏。理想很丰满，但实际跑起来经常陷⼊⽆效循环，输出不可控，⽬前更多是概念验证，⽣产环境基本不⽤。

4）SemanticKernel是微软出的，和Azure⽣态深度绑定，适合.NET技术栈的团队。它强调“规划器”概念，把任务拆解做成可配置模块，和LangChain类似但更重企业级控制。

5）Dify和FastGPT属于低代码平台型框架，把Agent的流程可视化，拖拽就能编排prompt、⼯具和逻辑。适合产品经理或业务⽅快速试错，但灵活性受限，复杂逻辑还得写代码。

总的来说，选哪个框架看场景。做RAG优先看LlamaIndex，要快速搭demo⽤LangChain或Dify，企业级可控流程可以看看 Semantic Kernel。

# 什么是 LangChain Agent?

LangChainAgent的本质是⼀个能做决策的“⼤脑”，它不直接⽣成最终结果，⽽是根据⽬标动态规划步骤，调⽤⼯具去执⾏。

1）Agent会接收⽤户输⼊，结合预设的提⽰词和可⽤⼯具描述，决定下⼀步动作。这个动作要么是调⽤某个⼯具（⽐如搜索、数据库查询），要么是直接返回结果。

2）它依赖LLM做推理判断。⽐如你问“今天上海天⽓怎么样”，Agent会先意识到需要实时数据，于是选择调⽤天⽓API⼯具，拿到结果后再让LLM汇总成⾃然语⾔回复。

3）⼯具（Tools）是关键组件，每个⼯具对应⼀个函数，声明了名称、描述和⼊参。Agent不直接写代码，⽽是通过描述理解⼯具能⼒。你可以接⼊SerpAPI做搜索，或者⾃定义⼀个查订单的函数。

// 伪代码⽰意：定义⼀个搜索⼯具

```txt
Tool searchTool = Tool.build()  
.name("search")  
.description("用于查询实时信息，比如天气、新闻")  
.function(query -> callSerpAPI(query))  
.build();
```

和普通Chain的区别在于，Chain是固定流程，Agent是动态路径。你没法提前预知它会怎么⾛，就像你不能预测⼈思考的过程。

适合场景：需要多步推理、外部数据获取、动态决策的任务。但如果逻辑简单，直接写Chain更⾼效，别为了⽤⽽⽤。

# 什么是 LangChain model?

LangChainmodel并不是⼀个独⽴的模型，它其实是LangChain框架中对各种⼤语⾔模型（LLM）的统⼀抽象封装。你⽤它来调⽤GPT、通义千问、ChatGLM这些模型时，接⼝都是⼀致的。

1）它的核⼼是提供⼀个标准接⼝，让开发者不⽤关⼼底层模型是哪家的，都能⽤同样的⽅式传⼊prompt、拿到输出。⽐如你切换从OpenAI到本地部署的Llama，代码改动可以⾮常⼩。

2）除了基础的⽂本⽣成，它还⽀持流式输出、带历史对话的会话模型（ChatModel）、以及结构化输出解析。像和⽤户多轮聊天的场景，直接⽤ RunnableWithMessageHistory 就能管理上下⽂。

# A2A协议的⼯作原理是怎样的？

A2A（Application-to-Application）协议不是某个具体的技术标准，⽽是⼀种通信范式，指的是应⽤系统之间通过定义好的接⼝直接交互。这种模式在微服务、中台架构⾥特别常⻅。

1）通常基于HTTP/HTTPS或消息队列实现，⽐如两个服务间⽤RESTfulAPI交换JSON数据，或者通过Kafka异步传递事件。关键在于双⽅约定好数据格式和调⽤语义。

2）安全控制很重要，⼀般会引⼊OAuth2、JWT做⾝份鉴权。⽐如⼀个订单系统调⽤库存系统时，必须携带有效token，对⽅验证通过才执⾏扣减操作。

3）为了降低耦合，很多公司会加⼀层API⽹关统⼀管理A2A流量。像阿⾥云的APIGateway就能做限流、监控、访问控制，后端服务只专注业务逻辑。

# A2A协议的⼯作流程是怎样的？

A2A（Application-to-Application）协议不是某个具体的标准协议，⽽是⼀类系统间通信模式的统称。它指的是两个应⽤程序直接通过API、消息或⽂件等⽅式交换数据，不依赖⼈⼯⼲预。

这类通信⼀般⾛服务间调⽤链路，常⻅于微服务架构。⽐如订单系统调⽤库存系统扣减接⼝，这就是典型的A2A场景。整个流程从发起⽅构造请求开始，经过⽹络传输，到达接收⽅处理并返回结果。

1）发起⽅应⽤准备好业务参数，封装成请求体

2）通过 HTTP/REST 或 gRPC 等协议发送到⽬标服务

3）⽬标服务接收到请求后解析参数，执⾏业务逻辑

4）将结果序列化为响应体返回给调⽤⽅

5）发起⽅根据响应做后续处理，如重试、落库或通知下游

如果是异步场景，会引⼊消息中间件。⽐如⽤户注册后需要发邮件、加积分，主流程写⼊消息队列，由消费者分别调⽤邮件服务和积分服务。这种情况下A2A的流转就变成了事件驱动，Kafka或RocketMQ扮演了关键⻆⾊。

# ⼤模型的结构化输出指的是什么？

⼤模型的结构化输出，说⽩了就是让模型不光吐⽂字，还能按指定格式返回数据，⽐如JSON、XML或特定schema的内容。你给个指令，它能⽣成符合接⼝契约的响应，⽽不是⼀堆⾃由发挥的⾃然语⾔。

这在实际系统集成⾥特别关键。⽐如你让⼤模型从⼀段⽂本⾥抽⽤户信息，直接回“张三，35岁，北京”还得再解析，但如果要求结构化输出，它就能直接给你：

```json
{"name":"张三"，"age":35，"city":"北京"}
```

这种能⼒⼀般靠提⽰词⼯程（promptengineering）引导，或者⽤像JSONmode这类机制强制约束输出格式。

OpenAI 的 API ⽀持 response_format={ "type": "json_object" } ，这时候模型就必须输出合法 JSON，否则调⽤⽅解析要出问题。

更进⼀步的做法是结合functioncalling或tooluse，把结构化输出当成调⽤外部⼯具的中间协议。⽐如你让模型判断是否需要查天⽓，它就返回⼀个带 function_call 字段的JSON，⾥⾯是函数名和参数，下游系统直接执⾏。

这类技术减少了后处理成本，让⼤模型能真正嵌⼊到软件流程⾥，⽽不是只当个聊天玩具。不过对模型本⾝的推理⼀致性和格式遵从度要求更⾼，⼩模型容易格式错乱，得反复校验。

# 解释LangChain框架中的Chain和Agent概念，并举例说明各⾃的应⽤场景

LangChain⾥的Chain和Agent是两个关键抽象，解决的是不同复杂度的任务编排问题。

Chain其实就是⼀个函数式的组合，把多个处理步骤像链条⼀样串起来。每个环节的输出⾃动作为下⼀个环节的输⼊，中间可以穿插对LLM的调⽤、数据处理或外部⼯具。⽐如你做客服机器⼈，⽤户问“今天北京天⽓怎么样”，你可以先⽤⼀个PromptTemplate构造查询语句，接着调⽤LLM解析出地点和需求，再交给⼀个WeatherTool获取真实数据，最后⽤另⼀个模板⽣成回复。这个流程就是典型的Chain，顺序执⾏，逻辑固定。

// 伪代码⽰意

String result $=$ chain.execute("今天北京天⽓如何？");

⽽Agent更灵活，它让LLM⾃⼰决定“下⼀步⼲什么”。LLM不只是回答问题，⽽是充当“决策⼤脑”，根据当前状态选择调⽤哪个⼯具、是否需要查数据库、要不要反复推理。⽐如做⼀个智能数据分析助⼿，⽤户说“帮我分析上周销售额下降的原因”，Agent可能先查销售表，再对⽐营销活动记录，发现某区域⼴告暂停后销量下滑，于是建议检查推⼴策略。整个过程路径不固定，由LLM动态规划。

1）Chain适合流程明确、步骤固定的场景，⽐如内容⽣成流⽔线、结构化信息提取

2）Agent 适合开放性任务，需要动态决策，⽐如智能客服、⾃动化运维诊断

3）Agent 的代价是性能开销⼤，因为每⼀步都要⾛ LLM 推理，容易陷⼊循环或误判

# 什么是⼤模型的"涌现能⼒"？列举三种典型表现并解释其可能成因

⼤模型的“涌现能⼒”指的是当模型参数规模达到某个临界点后，突然展现出⼩模型不具备的能⼒，这种能⼒⽆法通过简单外推得到。

1）上下⽂学习（In-Context Learning）

模型仅凭输⼊中的⼏个⽰例就能完成新任务，不需要额外微调。⽐如给GPT-3输⼊“苹果 ⽔果，胡萝⼘→蔬菜，番茄 $ ?$ ”它能推理出“蔬菜”。这背后其实是模型在推理时动态构建了内部计算路径，把提⽰词当成了临时指令模板。

2）思维链推理（Chain-of-Thought Reasoning）

模型能输出中间推理步骤，⽐如数学题先列式再求解。实验发现，只要在提⽰中加⼊“让我们⼀步步思考”，PaLM、GPT-3.5等模型就能激活这种⾏为。这说明⼤模型内部已经形成了类似推理的计算模式，但需要外部触发。

3）多任务泛化

同⼀个模型可以同时处理翻译、代码⽣成、逻辑判断等完全不同的任务，且表现接近专⽤模型。像Llama系列在训练时混⼊了海量多源数据，使得其权重空间⾃然分化出多个功能⼦空间。

可能成因在于：参数量突破临界点（⼀般认为要超60B）后，模型表达能⼒发⽣质变，⾼维空间中出现新的结构化组织⽅式。训练数据的多样性让模型学会了“元学习”⸺不是记答案，⽽是学怎么学。

假设需要让⼤模型⽣成⼀个React表单组件代码，请设计⼀个包含上下⽂约束的Prompt（需包含数据验证、错误提⽰等要求）

你让⼤模型写React表单，光说“写个表单”它肯定给你个最简单的input加按钮。要拿到能落地的代码，得把约束条件⼀次性给全。

关键是在Prompt⾥明确结构、⾏为和边界。⽐如你要⼀个⽤户注册表单，就得指定字段、验证规则、错误提⽰⽅式、提交逻辑。

可以这样组织上下⽂：

1）表单包含⽤户名、邮箱、密码、确认密码四个字段

2）所有字段必填，⽤户名⾄少3字符，邮箱格式校验，密码需8位以上且含⼤⼩写和数字

3）实时校验：输⼊时显⽰错误信息，不满⾜规则时禁⽤提交按钮

4）错误提⽰使⽤ React Hook Form 的 errors 对象驱动，配合 Zod 做 schema 校验

```javascript
const schema = z.object({

    confirmPassword: z.string()

    path: ["confirmPassword"]

```

搭配 useForm 和 zodResolver ，把 register 绑到输⼊框， errors 渲染提⽰，按钮根据formState.isValid 控制是否可点。

这种Prompt能让模型输出接近⽣产环境的代码，⽽不是玩具⽰例。你给的约束越贴近实际项⽬，⽣成结果越能直接⽤。

# 请描述使⽤LangChain构建⼀个⽂档问答系统的关键技术组件及实现步骤

构建⽂档问答系统，本质是把⾮结构化⽂本转成向量，再结合⼤模型做⾃然语⾔交互。LangChain提供了⼀整套⼯具链来简化这个过程。

# 1）⽂档加载与分割

先⽤DocumentLoaders从PDF、Word或⽹⻚抓取原始内容。拿到⽂本后得切分，⼀般按段落或固定⻓度（⽐如500token），太⻓会超出模型上下⽂，太短⼜丢失语义。这⾥常⽤ RecursiveCharacterTextSplitter。

# 2）向量化与检索

切好的⽂本块喂给嵌⼊模型（Embedding Model），⽐如 OpenAI 的 text-embedding-ada-002 或开源的 BGE。⽣成的向量存进向量数据库，像Chroma、Pinecone或Milvus。⽤户提问时，系统先把问题向量化，去库⾥找最相似的top-k⽂本块，这叫相关性检索。

# 3）提⽰⼯程与模型调⽤

检索到的上下⽂拼上⽤户问题，组装成 prompt，丢给⼤语⾔模型（LLM）。LangChain 提供 PromptTemplate 来规范格式，避免模型胡说。典型的模板就是“根据以下内容回答问题：{context}问题：{question}”。

# 4）链式调⽤（Chain）

把上述步骤串起来⽤LLMChain或RetrievalQA链。RetrievalQA是现成的⾼级封装，⼀⾏代码就能连起检索器和LLM，适合快速搭建原型。

# 假设要开发⼀个智能⼯单分类系统，请拆解AI可参与的环节并说明技术选型思路

智能⼯单分类不是简单打个标签，得把AI嵌进整个流转链条⾥，哪⾥能省⼈⼒、提准确率就往哪插。

1）⼯单预处理阶段，⽂本清洗和标准化可以⽤规则 $\mid +$ 轻量模型。⽐如⽤户输⼊“登不录”，先⽤正则和纠错词典做基础清洗，再上⼀个TinyBERT做语义对⻬，转成标准表述“⽆法登录系统”。这步别上⼤模型，响应延迟扛不住。

2）核⼼分类环节看数据量和类⽬复杂度。如果只有⼏⼗个固定类别，RoBERTa $^ +$ CRF⾜够，推理快、好维护。要是类⽬动态增⻓，⽐如每天新增业务线，就得考虑 Prompt Learning 配合 P-tuning v2，接通⼤模型如 ChatGLM-6B 做zero-shot分类，类⽬⼀改prompt跟着变，不⽤重新训练。

3）后置反馈闭环必须做。分错的⼯单要进⼈⼯复核池，这部分数据定期回流做增量训练。可以搭个轻量LabelStudio$^ +$ Milvus相似样本检索，⾃动推荐历史相似案例给标注员，效率翻倍。

4）⼯程部署上，⼩模型⾛TensorFlowLite或ONNXRuntime嵌⼊服务内部，⼤模型⽤vLLM做批处理异步推理。别把所有请求都怼到⼤模型上，成本直接炸。

处理超⻓上下⽂，本质是绕过或优化模型的token⻓度硬限制。直接喂满动辄32K、128K上下⽂，成本⾼且效果不⼀定好，得靠⼯程⼿段拆解。

# 1）分块与索引检索

把⻓⽂档切⽚存⼊向量数据库，⽐如⽤LangChain $^ +$ Chroma/Pinecone，查询时只召回相关 chunk。关键在分块策略，按段落切可能割裂语义，结合滑动窗⼝重叠（overlap）能缓解。但太碎了会丢失全局逻辑。

# 2）摘要增强（Summary Augmentation）

对历史对话或⽂档提前⽣成摘要，新请求到来时，把摘要当上下⽂注⼊。像LLM-poweredsummarizer在对话系统⾥很常⻅，能把前10轮压缩成1-2句，省下⼤量token。

# 3）位置插值（Position Interpolation）

针对 Transformer 架构的位置编码做⼿脚。原⽣ RoPE ⽀持外推但衰减快，采⽤ NTK-by-parts 或 YaRN 等⽅法，在推理时动态调整位置频率，让模型“脑补”超出训练⻓度的位置信息。实测能在32K模型上跑64K输⼊，效果接近原⽣⻓上下⽂。

# 4）侧边缓存（Side Cache）

Google 提出的思路，把已计算的 KV 缓存复⽤起来。⽐如⽤户修改了 prompt 中⼀⼩段，不需要全量 recompute，命中部分直接从cache读。适合交互式场景，降低延迟和算⼒消耗。

# 5）分层上下⽂路由

复杂系统如Agent⼯作流，⽤调度层决定哪些信息进⻓期记忆（vectorstore），哪些放短期上下⽂。AutoGPT类项⽬就这么⼲，核⼼状态放context，细节查数据库。

# 当⼤模型API响应延迟超过1秒时，前端可以采取哪些优化策略保证⽤户体验？

前端能做的其实很有限，核⼼是“让⽤户感觉快”，⽽不是真的让模型变快。⼤模型API本⾝耗时主要在服务端推理，前端更多是体验层的兜底。

1）请求发出去之后，⽴刻给⽤户反馈，别⼲等。⽐如⻢上展⽰⼀个“思考中...”的动画或者⻣架屏，告诉⽤户系统已经在处理了，避免误操作重复提交。

2）如果接⼝超过800ms还没回来，可以主动提⽰“⽣成时间较⻓，请稍候”。这种预期管理很重要，⽤户知道要等，就不会觉得卡死了。

3）优先考虑流式响应（streaming）。让后端以SSE或WebSocket⽅式分段返回结果，前端拿到⼀段就渲染⼀段。就像ChatGPT那样逐字输出，视觉上⽐等1秒再刷出来舒服得多。

4）结合loading状态和取消按钮。允许⽤户在等待时⼿动中断请求，提升控制感。特别是移动端，⻓时间⽆响应容易引发焦虑。

5）缓存历史问答对。对于常⻅问题，⽐如产品FAQ，可以直接⾛本地缓存秒回，根本不⽤⾛⼤模型。

6）降级策略。检测到连续超时，可以⾃动切换到轻量模型接⼝或静态回答模板，保证基础可⽤性。

# 使⽤LangChain时，如何实现多路召回结果的动态权重分配？

多路召回的动态权重分配，关键在于根据查询实时计算各路结果的置信度或相关性得分，⽽不是⽤固定权重拍脑袋。

1）最直接的做法是引⼊⼀个重排序模型（Reranker），⽐如 BGE-Reranker 或 Cohere Rerank。把不同来源召回的候选集合并后，统⼀喂给Reranker打分，它会输出基于query的相关性排序，⾃然就实现了“动态加权”。LangChain⾥可以⽤ RunnableLambda 包装 reranker 调⽤。

2）另⼀种思路是基于查询特征做路由加权。⽐如⽤户问的是时间敏感问题，就提⾼来⾃新闻索引或时序数据库那⼀路的权重；如果是专业术语，就抬⾼知识图谱或维基数据源的分值。这在LangChain可以通过 RouterRetriever 实现，配合LLM判断query类型，动态选择或加权⼦检索器。

3）还可以让LLM⾃⼰评估各路结果的相关性。把每路召回的top-k和query⼀起输⼊LLM，让它打分或排序。虽然贵点慢点，但灵活性最⾼，适合对效果要求极⾼的场景。

代码上，核⼼是组合多个 BaseRetriever 并在外层做融合：

from langchain.retrievers import EnsembleRetriever

重点是 weights 别写死。你可以先跑个轻量模型预估各路匹配质量，再填进去。像JinaReranker、M3E+BGE组合在C-MTEB上能涨5~8个点，⽐静态融合强不少。

# 当⼤模型上下⽂窗⼝扩展到100万token时，哪些现有业务场景可能发⽣质变？

上下⽂窗⼝突破百万token，最直接的影响是模型能“看⻅”和处理的信息⻓度远超以往。以前处理⻓⽂本得切⽚、摘要、丢信息，现在可以直接喂完整⽂档，很多场景的实现⽅式会彻底改变。

4）客服和企业知识库的体验升级。传统RAG⾯对复杂问题经常答⾮所问，因为检索⽚段有限。百万上下⽂下，可以直接加载整个产品⼿册或历史⼯单，回答更完整准确。

# 当发现RAG系统召回结果与⽤户query意图不匹配时，有哪些可能的改进⽅向？

RAG系统召回结果偏离⽤户意图，问题通常出在检索和⽣成两个环节的衔接上。先定位是“没找到”还是“找到了但没⽤好”。

1）优化检索阶段的语义匹配能⼒

query 本⾝可能有歧义或表述不清晰，直接搜容易翻⻋。可以⽤ query 改写来增强表达，⽐如⽤⼤模型把原始 query扩展成多个相关问法，再并⾏检索。像LangChain提供了 MultiQueryRetriever 就是⼲这个的。另外，embedding模型是否适配业务场景也很关键，通⽤模型如text-embedding-ada-002在垂直领域可能不如微调过的BGE 或 $\mathfrak { m } 3 \mathfrak { e } _ { \circ }$ 。

2）提升⽂档切分的合理性

chunk太⼤，关键信息被稀释；太⼩，上下⽂丢失。⼀般建议按语义切分，⽐如⽤LangChain的RecursiveCharacterTextSplitter 结合 sentence transformers 做句⼦边界感知。chunk size 控制在$2 5 6 { \sim } 5 1 2$ token⽐较常⻅，具体得看内容密度。

3）引⼊重排序（Rerank）机制

初检可能召回⼀堆相关度⼀般的⽂档，加⼀层cross-encoder重排能显著提升TopK质量。像Cohere的reranker、bge-reranker都可以直接调⽤，把最相关的⼏个往前顶，让LLM看到更准的信息。

4）调整⽣成阶段的提⽰⼯程

有时候检索是对的，但prompt写得太松，模型⾃⼰脑补。要明确约束“基于以下上下⽂回答”，并在输⼊⾥只放⾼相关度的chunk。也可以做query路由，判断是否⾛检索流程，避免⽆关query强⾏查库。

# 使⽤LangChain实现RAG系统时，如何处理PDF⽂档中的表格数据召回问题？

PDF⾥的表格数据在RAG⾥是个硬⻣头，因为传统⽂本切⽚会把表格拆得⽀离破碎，导致召回时压根不完整。LangChain本⾝不直接解析表格，得靠外部⼯具先把表格结构化。

1）先⽤ PyMuPDF 或 pdfplumber 提取PDF中的表格，保持⾏列结构，转成HTML或Markdown格式存储。⽐如⼀个财务报表，直接按⽂本切⽚会丢失表头和对应关系，⽽⽤pdfplumber能还原成真正的⼆维结构。

2）把结构化后的表格内容作为独⽴⽂档单元（Document）传给LangChain，设置特殊元数据标记，⽐如{"source_type": "table", "page": 5} ，⽅便后续检索时识别来源。

3）向量化时，表格整体作为⼀个chunk嵌⼊，避免⾏级拆分。可以配合Chroma或FAISS做混合检索，在查询时判断是否涉及“⾦额”、“统计”等关键词，动态提升表格类chunk的召回权重。

4）如果表格特别⼤，考虑⽤“表头 $^ +$ ⾏”组合⽅式⽣成多个⼦chunk，但每条都保留完整表头信息，确保语义完整。

```python
doc = Document(
    page_content=markdown_table, # 结构化后的表格
    metadata={'type':'table','page':'parenum}
)
```

整个流程关键在于提前结构化，⽽不是指望向量模型⾃⼰理解破碎的表格⽂本。很多RAG效果差，其实是数据预处理没做好这⼀步。

# 什么是RAG中的Rerank？具体需要怎么做？

RAG⾥的Rerank其实就是对检索阶段召回的多个⽂档⽚段，重新打分排序，挑出最相关的结果喂给⼤模型⽣成答案。

⼀般流程是先⽤向量数据库做相似度搜索，⽐如从知识库⾥找出top-5的候选⽂档。但向量检索有个问题，它只看语义相似，不⼀定和⽤户问题真正匹配。这时候就需要Rerank模型再筛⼀遍。

Rerank 模型通常是交叉编码器（Cross-Encoder），⽐如 BGE-Reranker 或 Cohere Rerank API。它会把⽤户问题和每个召回的⽂档拼在⼀起输⼊模型，输出⼀个相关性分数。这个过程⽐向量检索慢，但精度⾼得多。

具体做法很简单，假设你有5个候选段落：

1）把query和每个段落组合成⼀对⽂本2）送进Rerank模型得到相关性得分3）按得分从⾼到低排序，取前2~3个⾼质量段落输⼊LLM

代码上类似这样：

# 伪代码⽰意

```hcl
pairs = [(query, doc) for doc in retrieved_docs]  
scores = reranker.predict(pairs)  
ranked_docs = [doc for _, doc in sorted(zip(scores, retrieved_docs), reverse=True)] 
```

要不要加Rerank得看场景。如果你的系统能接受⼀定噪⾳，直接⽤向量检索也⾏。但要是追求准确率，尤其是客服、医疗这类容错低的场景，这⼀步的提升⾮常明显，基本能提 $1 0 \% { \sim } 2 0 \%$ 的最终回答准确率。

# 什么混合检索？在基于⼤模型的应⽤开发中，混合检索主要解决什么问题？

混合检索不是简单把关键词和向量拼在⼀起。它要解决的是单⼀检索⽅式的短板，⽐如纯关键词匹配会因为字⾯不⼀致丢内容，纯向量检索⼜可能偏离精确条件。

1）关键词检索基于倒排索引，查的是词频和位置，适合处理明确实体、过滤条件，像“2024年发布的⼿机”。但遇到语义相近表达，⽐如“续航强”和“电池耐⽤”，就容易漏。

2）向量检索把⽂本映射到语义空间，靠相似度打分，能捕捉“⾼性能⼿机”和“游戏⼿机”这种隐含关联。问题是没法精准控制范围，⽐如指定价格区间或品牌，还可能把“苹果⼿机”和“⽔果苹果”搞混。

混合检索的关键是融合策略。常⻅做法是分别召回结果，再⽤加权、交叉排序（RRF）合并。⽐如 Elasticsearch 的query_then_fetch 结合 knn 查询，或者⽤ RAGFlow、LlamaIndex 这类框架统⼀调度。

这招在问答系统、知识库检索⾥特别实⽤。你既要语义理解能⼒，⼜要⽀持字段过滤和精确匹配，光靠⼤模型⽣成不⾏，得靠混合检索把底座打好。

# 在RAG应⽤中为了优化检索精度，其中的数据清洗和预处理怎么做？

数据清洗和预处理在RAG中直接决定检索质量，很多效果差的问题其实都出在这⼀步。

1）⽂本切分要合理，不能简单按固定⻓度硬切。⽐如⽤ LangChain 的 RecursiveCharacterTextSplitter时，得保留段落上下⽂，避免把⼀句话从中间劈开。⼀般 chunk size 设成 5121024 token，overlap 保持 100200token，让前后⽂能衔接。

2）清理噪声是脏活累活。HTML标签、⼴告⽂本、⽆意义的符号都得去掉。可以⽤ BeautifulSoup 或trafilatura 提取正⽂，再通过正则过滤掉乱码和特殊字符。像维基百科这类数据源，还得剔除参考⽂献、编辑提⽰这些⾮主体内容。

3）元数据注⼊很关键。给每个chunk加上来源URL、标题、章节名等信息，召回时能结合上下⽂重排序。⽐如同⼀个⽂档的不同⽚段，可以通过 source 字段做去重或聚合。

4）编码统⼀别忽视。所有⽂本转成UTF-8，避免后续向量化时报错。中⽂场景下还要考虑繁简归⼀化，像“数据库”和“資料庫”最好映射到同⼀语义空间。

5）可选做实体增强。⽤spaCy或HanLP抽关键词、⼈名、地名，附加到chunkmetadata⾥，在检索时⽀持基于实体的扩展查询。

整个流程可以串成pipeline，⽤ApacheBeam或Airflow调度，确保数据进Embedding模型前是⼲净、结构化、带上下⽂的。

什么查询扩展？为什么在RAG应⽤中需要查询扩展？

查询扩展本质是把⽤户那句简单的原始问题，变形成⼀个或多个更完整、信息更丰富的查询语句。你别⼩看这⼀步，它直接决定了后续检索能不能捞出真正相关的内容。

1） ⽤户搜“苹果⼿机续航差”，其实他关⼼的是 iPhone 15 Pro 的电池表现和省电技巧。原始 query 太短，关键词稀疏，直接去向量库搜索容易匹配到⽆关的“苹果⽔果”或者泛泛的“⼿机耗电”。这时候就得靠查询扩展来补全意图。

2）常⻅做法有⼏种。⼀种是同义词/近义词扩写，“续航”换成“电池寿命”“使⽤时间”；⼀种是基于⼤模型做多跳推理，让LLM把原始问题拆成⼏个⼦问题，⽐如“iPhone15Pro满电能⽤多久”“哪些设置能延⻓待机”；还有⼀种是查询重写，把⼝语化表达转成更标准的检索语⾔。

3）不做查询扩展的RAG系统，召回率通常很低。特别是⾯对缩写、俚语、模糊表达时，向量检索压根不经过语义深化，直接就去算相似度，结果就是top-k⽂档⾥没有命中关键段落。像LangChain、LlamaIndex都内置了querytransformation模块，就是为了解决这个断层。

这步看着是脏活累活，但它是连接“⼈话”和“机器可检索语义”的关键桥梁。搞不定查询扩展，RAG效果就很难稳定。

# 如何进⾏RAG调优后的效果评估？请给出真实应⽤场景中采⽤的效果评估标准与⽅法

RAG系统调优后不能只看⽣成结果“好不好”，得⽤量化指标和真实场景反馈来判断是否真的提升了效果。重点是结合⾃动评估指标和⼈⼯评估，覆盖相关性、准确性和可⽤性。

1）先看召回阶段，⽤传统信息检索指标。⽐如在企业知识库问答场景中，我们拿1000条历史⽤户问题做测试集，计算 top-5 ⽂档的 Recall@5 和 MRR。如果 Recal $\ @ 5$ 从0.6提升到0.78，说明检索更准了，这是硬指标。

2）再看整个RAG流程的输出质量。可以⽤Rouge-L衡量⽣成答案与标准答案的⽂本相似度，但别太依赖它。更关键的是BERTScore或BARTScore，它们能更好捕捉语义匹配程度。⽐如在客服机器⼈中，我们发现Rouge-L变化不⼤，但 BERTScore 提⾼了 $1 2 \%$ ，实际回答更贴切了。

3）引⼊事实⼀致性检测。⽤Faithfulness指标判断⽣成内容是否基于检索到的⽂档。⽐如模型说“报销周期是7天”，但⽂档写的是“5个⼯作⽇”，这就是幻觉。可以⽤专⻔打分模型如RAGAS来量化。

4）最终绕不开⼈⼯评估。设计评分卡，让业务⼈员从相关性、准确性、完整性、可读性四个维度打分。⽐如在⾦融投研场景，分析师对调优前后的回答盲评，发现新版本在“数据来源清晰”这⼀项得分提升明显。

真实项⽬⾥，像⽤ LangChain $^ +$ Pinecone做法律咨询系统时，就是靠这套组合拳验证调优有效，上线后⼀次解决率提⾼了 $23 \text{‰}$ 。

选嵌⼊模型其实是个权衡过程，关键得看你的数据、场景和系统约束。

⾸先语⾔要对⻬。如果你的业务全是中⽂，直接上multilingual或专⻔训过的中⽂模型，⽐如bge-base-zh这类，英⽂为主的模型在中⽂语义上容易翻⻋。反过来如果是多语⾔混合，可以考虑 mxbai、bge-m3 或 sentence-transformers 的多语⾔系列。

其次看向量质量与维度。⾼质量模型输出的向量更稠密，召回准确率⾼，但维度也⾼，⽐如768维会⽐384维占更多内存和计算资源。你要评估检索精度和性能之间的平衡。⼀般⼩模型适合轻量应⽤，⼤模型⽤在对相关性要求⾼的场景，像客服问答、精准推荐。

上下⽂⻓度也得留意。有的模型最⼤只⽀持512token，处理⻓⽂档时会被截断，语义就残了。如果做法律、论⽂这类⻓⽂本 RAG，得选⽀持 8k 甚⾄ 32k 的模型，⽐如 bge-large 或者 jina-embeddings-v2。

推理成本不能忽视。开源模型⾃⼰部署可控，但要搞GPU推理服务，延迟和吞吐得压得住。如果不想管infra，可以直接调⽤ API，⽐如阿⾥云的通义embedding、OpenAI 的 text-embedding-ada-002，省事但⻓期调⽤量⼤会贵。

最后还得和检索器匹配。⽐如你⽤FAISS做近似搜索，低维向量 $^ { \cdot + }$ 余弦相似度效果好；要是⽤Elasticsearch向量库，可能就得适配它的距离函数。

⼀句话：模型不是越⼤越好，⽽是要跟数据、系统、成本三匹配。

# 在RAG中，索引流程中的⽂档解析你们怎么做的？

⽂档解析其实是RAG系统⾥特别关键的⼀步，搞不定这环，后⾯embedding再准也没⽤。我们⼀般不会直接扔原始⽂件给模型，得先把PDF、Word、HTML这些格式拆成⼲净的⽂本块，还得保留必要的结构信息。

1）先⽤通⽤解析⼯具做预处理。⽐如PDF⽤PyMuPDF或pdfplumber，能精准提取⽂字和分⻚；Office⽂档⽤ApacheTika，它⽀持格式多，省⼼得多。HTML就⽤BeautifulSoup去掉脚本和⼴告这类噪⾳。

2）接着是分块策略。不能简单按段落切，否则会把上下⽂割裂。我们会结合语义边界，⽐如标题层级变化时强制分块，同时控制每块在 300~500 token 左右。像 LlamaIndex 或 LangChain 提供的 RecursiveCharacterTextSplitter 就挺好⽤，能优先按 \n\n 、句号这些符号切分。

3）结构化信息保留也很重要。⽐如从企业⽂档中抽章节标题，打上 sectio $1 = 3 . 1$ 这样的元数据，后续检索时能结合标题过滤，召回准确率能提 $2 0 \%$ 以上。

代码上基本⻓这样：

```python
from langchain.text splitter import RecursiveCharacterTextSplitter  
splitter = RecursiveCharacterTextSplitter(  
    chunk_size=400,  
    chunk_overlap=50,  
    separators=['\n\n", "\n", "", "."]  
)  
chunks = splitter.split_text(text) 
```

整个过程其实就是在“保语义”和“控⻓度”之间找平衡，太碎了影响上下⽂理解，太⼤了⼜容易混⼊⽆关内容。

# 向量数据库原理是什么？请简述下它的原理

向量数据库本质是为⾼维向量数据设计的存储与检索系统，核⼼⽬标是在亿级向量中快速找到和查询向量最相似的那些。

传统数据库⽤B+树做精确匹配或范围查询，但向量相似性搜索要的是“近似”，⽐如余弦相似度、欧⽒距离。如果暴⼒遍历所有向量算距离，1亿个向量每个128维，⼀次查询就得⼏⼗毫秒甚⾄上百毫秒，根本扛不住。所以关键在于近似最近邻搜索（ANN）算法，在可接受精度损失下把查询从O(n)降到O(logn)甚⾄常数级。

常⻅实现⽅式有⼏种：

1）基于局部敏感哈希（LSH），把相近向量以更⾼概率映射到同⼀个桶⾥，适合⾼维稀疏场景，但召回率波动⼤；

2）基于树结构如随机投影树，划分空间，但⾼维下效果退化明显；

3）最主流的是图-based⽅法，⽐如HNSW（Hierarchical Navigable Small World），构建多层导航图，顶层稀疏快速定位⽅向，底层精细搜索，能在毫秒内完成百万级查询，Milvus、Pinecone都在⽤。

另外，向量数据库通常会结合标量索引做混合查询，⽐如“找和这个图⽚相似且上传时间在最近7天的”。这就需要⽀持结构化字段过滤 $^ +$ 向量检索的联合优化。

向量数据库中的HNSW、LSH、PQ分别是什么意思？

HNSW、LSH、PQ是向量数据库⾥常⽤的近似最近邻搜索（ANN）技术，⽤来在⾼维空间快速找相似向量，毕竟暴⼒遍历O(n)在亿级数据上根本扛不住。

1）HNSW（Hierarchical Navigable Small World）本质是个多层图结构。每⼀层都是个近邻图，⾼层稀疏⽤来“跳”得快，底层密集做精细搜索。查询时从顶层开始往下⾛，像导航⼀样逐步逼近⽬标点。Milvus、Weaviate都⽤它，召回率⾼，延迟也稳，但建索引内存开销⼤。

2）LSH（Locality-SensitiveHashing）思路更粗暴：把相似的向量通过特定哈希函数尽可能甩到同⼀个桶⾥。查的时候只搜对应桶，⼤幅缩⼩范围。优点是实现简单、存储省，但召回率不如HNSW，尤其分布不均时容易漏。早期Annoy ⽤过类似思想。

3）PQ（ProductQuantization）⼲的是降维压缩的脏活。它把⾼维向量切成⼏段，每段独⽴聚类，⽤聚类中⼼代替原始向量分量，存个码本就⾏。原来128维float能压到16字节内，检索时⽤对称距离近似算相似度。Faiss就拿它和IVF搭配，扛住了⼗亿级向量库。

![image](https://cdn-mineru.openxlab.org.cn/result/2026-04-10/a4546dd9-d3cc-4d94-90fb-a52fb3050fc3/7b4d01ea0420e296817af93746ba08b717a5df5b4e500454aad5aa927581075c.jpg)


这仨经常混着⽤，⽐如Faiss⾥IVFPQ就是先⽤聚类定位候选集，再PQ压缩算距。选哪个看场景：要精度选HNSW，要省资源可以试LSH+PQ组合。

# 向量数据库中的ANN是什么？为什么需要⽤它？

近似最近邻（ANN）是向量数据库⾥⽤来加速相似性搜索的核⼼技术。原始的暴⼒搜索要算查询向量和所有向量的距离，数据量⼀⼤，⽐如上亿条，根本没法实时响应。ANN的思路就是牺牲⼀点点精度，换来⼏倍甚⾄上百倍的速度提升。

它通过构建特殊的索引结构来缩⼩搜索范围。常⻅的⽅法有：

1）基于图的HNSW，把向量连成近邻图，从⼀个⼊⼝点开始“爬⼭”，逐步逼近最近的邻居。Faiss和Milvus都⽀持这种，效果好，吞吐⾼。

2）基于聚类的IVF，先把向量聚成若⼲簇，搜索时只查离查询点最近的⼏个簇，避免全量扫描。适合⼤数据集，配合PQ编码还能⼤幅降内存。

3）基于LSH的哈希映射，把相似向量尽量散列到同⼀个桶⾥，但召回率在⾼维下容易掉得厉害，现在⽤得少了。

![image](https://cdn-mineru.openxlab.org.cn/result/2026-04-10/a4546dd9-d3cc-4d94-90fb-a52fb3050fc3/6e9e8272dcb3b315cfd795bd644110f625651599703470769b3c9cb5ec0a19f3.jpg)


为什么⾮要⽤它？因为纯brute-force在千万级以上向量场景下，延迟动辄⼏百毫秒甚⾄秒级，压根不经过。⽽ANN能把响应控制在⼏毫秒内，才能⽀撑推荐、图⽂搜、语义匹配这些实时业务。像推荐系统⾥⽤户⼀刷就触发⼀次向量化检索，不⽤ANN根本扛不住。

# 向量数据库的⼯作流程有哪些？请简述下

向量数据库不是简单存个数组就完事了，它得解决“相似性检索”这个核⼼问题。整个流程从数据进来开始，到最后返回结果，每⼀步都围绕⾼效近似最近邻搜索展开。

1）数据预处理阶段，原始数据⽐如⽂本、图⽚先过嵌⼊模型，转成⾼维向量。这步通常在外部做，⽐如⽤Sentence-BERT 或 CLIP 模型⽣成向量，维度常⻅ 384 到 1024。

2）向量写⼊时，数据库会做索引构建。直接暴⼒计算所有距离肯定搞不定，所以要⽤专⻔的索引结构，⽐如HNSW构建图索引，IVF做聚类分组，或者PQ做量化压缩。这些技术能让查询时跳过⼤部分不相关的向量。

3）查询阶段，输⼊⼀个⽬标向量，系统先定位可能相近的候选集。⽐如HNSW从⼊⼝点出发沿图遍历，IVF先算落在哪个聚类中⼼附近，再只搜那个分区⾥的向量。最后对候选集做精确距离计算，返回Top-K最相似的结果。

整个过程的关键在于平衡精度和性能。索引构建会影响写⼊速度和内存占⽤，⽽搜索策略决定延迟和召回率。典型产品像 Milvus、Pinecone、Weaviate 都是基于这类流程设计的。

# PEFT是什么？为什么需要PEFT？

PEFT全称是Parameter-EfficientFine-Tuning，直⽩点说就是“只动⼀⼩部分参数来微调⼤模型”。现在⼤模型动不动就上百亿、上千亿参数，⽐如Llama、ChatGLM这种，直接全量微调成本太⾼了，显存、算⼒、时间都吃不消。

其实我们发现，微调的时候没必要更新所有参数。PEFT的思路是冻结原模型绝⼤部分权重，只训练少量额外引⼊或选中的参数，就能达到接近全量微调的效果。这样显存能省下 $7 0 \%$ 以上，训练速度也快很多，普通⼏张卡甚⾄单卡也能搞。

常⻅的PEFT⽅法⾥，LoRA是最⽕的。它在原始层旁边加个低秩矩阵做增量，训练时只更新这个⼩矩阵。⽐如⼀个7B模型，⽤LoRA可能只改 $0 . 1 \%$ 的参数，效果却不差。HuggingFace的 peft 库已经⽀持得⾮常好，配合transformers 能轻松上⼿。

代码⻓这样：

```python

```

```python
model = get_peft_model(model, lora_config) 
```

除了LoRA，还有Adapter、Prefix-tuning等⽅法，但LoRA因为⽆推理延迟、实现简单，成了主流选择。特别是资源有限⼜想定制⼤模型的场景，⽐如企业私有模型微调，PEFT⼏乎是标配⽅案。

# 参数⾼效微调（PEFT）的核⼼思路是什么？列举3种典型⽅法

参数⾼效微调的核⼼思路是只微调模型中极⼩⼀部分参数，冻结绝⼤部分原始参数，从⽽在保持下游任务性能的同时，⼤幅降低计算和存储开销。

⼤模型动辄上百亿参数，全量微调需要⼏⼗甚⾄上百GB显存，普通团队根本搞不定。PEFT的做法是“以⼩博⼤”，通过引⼊少量可训练参数来适配新任务，⽐如只调 $0 . 1 \% { \sim } 1 \%$ 的参数就能达到接近全量微调的效果。

# 1） LoRA（Low-Rank Adaptation）

在原始权重旁注⼊低秩矩阵，训练时只更新这些⼩矩阵。推理时可以合并到原权重中，完全不增加推理延迟。HuggingFace Transformers 已深度集成，现已成为主流选择。

# 2） Adapter

在Transformer模块间插⼊⼩型前馈⽹络（通常两层MLP），原模型冻结，只训练插⼊的模块。虽然效果好，但会增加推理延迟，因为每次前向都要⾛额外⽹络。

# 3） Prompt Tuning / Prefix Tuning

通过可学习的“软提⽰”向量引导模型输出，本质是把任务建模成“填提⽰”的过程。PrefixTuning把这些向量拼接在每⼀层输⼊前，PromptTuning只加在第⼀层。节省参数，但对初始化敏感，⼩模型上容易不稳定。

# PEFT和全量微调的区别？

PEFT本质上是解决⼤模型微调成本太⾼的问题。全量微调要更新整个模型所有参数，显存和计算资源消耗巨⼤，⽐如⼀个13B的模型，光梯度存储就得上百GB显存。

⽽PEFT的思路是冻结原模型⼤部分参数，只训练⼀⼩部分新增或改造的模块。这样⼀来，显存占⽤能降到原来的1/10甚⾄更低，普通单卡也能跑。

1）全量微调：每个参数都参与更新，效果理论上最好，但训练慢、成本⾼，需要完整的优化器状态和梯度保存。适合有充⾜算⼒且对性能极致要求的场景，⽐如公司级训练集群搞通⽤能⼒升级。

2）PEFT ⽅法：以 LoRA 为例，它在原始权重旁并⾏注⼊低秩矩阵，训练时只更新这些⼩矩阵。假设原始权重是 $W\in \mathbb{R}^{768\times 768}$，LoRA 拆成两个⼩矩阵 $A \in \mathbb{R}^{768\times r}$ 和 $B \in\mathbb{R}^{r\times 768}$，其中 $\$ 1$ 通常设为8或 $1 6 .$ 。这样可训练参数数量从⼏⼗亿骤降到百万级。

// 伪代码⽰意 LoRA 注⼊

Matrix $\textsf { W } =$ loadOriginalWeight(); // 冻结

Matrix A = randomInit(768, 8); // 可训练

Matrix $\textsf { B } =$ randomInit(8, 768); // 可训练

Matrix loraOutput $=$ input $^ *$ $( \mathsf { W } + \mathsf { A } ^ { \mathrm { ~ * ~ } } \mathsf { B } )$ ); // W 不更新

常⻅变体还有 Adapter Tuning、Prefix Tuning 等，但 LoRA 因其不改变推理结构、兼容性好成为主流。HuggingFace的 peft 库已经⽀持多种模式，配合 transformers ⼏⾏代码就能上。

效果上，多数任务中LoRA能达到全量微调 $9 5 \%$ 以上的性能，但对强推理或复杂指令遵循任务可能略有差距。关键是省了太多资源，让7B/13B模型在消费级GPU上也能快速迭代。

# 在进⾏Fine-Tuning时，如何选择适合的预训练模型？

这个问题其实是在问怎么给特定任务挑⼀个合适的预训练模型来微调，关键不是模型越⼤越好，⽽是看匹配度和资源约束。

1）先看任务类型对不对⼝。⽐如做中⽂⽂本⽣成或理解，那肯定优先选在中⽂语料上预训练过的模型，像 Qwen、ChatGLM这类原⽣⽀持中⽂的系列就⽐纯英⽂的LLaMA更合适。语⾔不匹配的话，再⼤的参数量也搞不定语义理解。

2）再看模型规模和你的算⼒能不能对上。7B参数的模型⽤单卡A100能跑，但如果是70B，就得考虑模型并⾏或者直接上云了。⼀般情况下，中⼩公司做垂直场景微调，7B左右的模型性价⽐最⾼，显存压得下来，训练时间也扛得住。

3）还要看预训练数据的时间范围和领域。⽐如你要做⾦融研报⽣成，最好选那些在财经⽂本上持续预训练过的模型，⽽不是通⽤语料训完就停的。有些开源模型会标明训练数据来源和时间，这点要仔细查⽂档。

4）最后看微调⽣态⽀不⽀持。像HuggingFace上有⼤量基于LLaMA系列的LoRA微调⼯具链，如果你选了⼀个冷⻔模型，可能连适配的Trainer都没有，脏活累活都得⾃⼰写。

代码上其实就是加载不同 checkpoint 的区别：

```python
from transformers import AutoTokenizer, AutoModelForCausalLM  
tokenizer = AutoTokenizer.from_pretrained("qwen-7b")  
model = AutoModelForCausalLM.from_pretrained("qwen-7b") 
```

换模型时路径⼀改就⾏，但背后的数据和架构差异决定了效果上限。

# 微调中常⽤的优化器有哪些？

微调⼤模型时选优化器，关键得平衡收敛速度和训练稳定性。常⻅的⼏种其实都源⾃梯度下降的改进思路。

1）SGDwithMomentum算是⽼前辈了，加个动量项能让参数更新不那么容易在平坦区域震荡。但学习率敏感，调不好容易不收敛，现在⼤模型微调⽤得少了。

2）Adam最常⻅，⼏乎成了默认选项。它⾃适应调整每个参数的学习率，对稀疏梯度特别友好。BERT、RoBERTa这些预训练模型做下游任务微调时，基本都拿Adam打底。不过内存开销⼤，因为要存每个参数的⼀阶⼆阶梯度。

// PyTorch 伪代码⽰意，实际不⽤ Java 写训练

optimizer $=$ torch.optim.Adam(model.parameters(), lr=2e-5) 

3）AdamW是Adam的升级版，把权重衰减从梯度更新⾥拆出来单独算，解决了Adam在正则化上的理论缺陷。Hugging Face Transformers ⾥默认推荐的就是 AdamW，像微调 BART 或 T5 都这么配。

4）Lion是较新的选择，Google提出来的，只⽤⼀阶动量，内存⽐Adam少⼀半，⽽且在某些NLP任务上效果更好。但它对学习率更敏感，需要更精细地调参。

总的来说，AdamW因为稳定性和效果兼备，成了当前主流选择。⼩规模实验可以试试Lion看能不能提速，⽼项⽬可能还在⽤Adam。SGD基本只出现在特定场景，⽐如某些视觉模型微调还会⽤。

# 如何判断微调效果是否达到预期？

微调效果能不能扛住业务，得靠数据说话，不能拍脑袋。

1）先看基础指标，⽐如分类任务的准确率、F1值，⽣成任务的BLEU、ROUGE。这些是硬指标，训练集和验证集上的提升得稳定，⼀般要求验证集指标⽐基线模型⾼ $5 \%$ 以上才算有显著收益。

2）光看数字不够，得做⼈⼯评估。抽样⼀批模型输出，让业务⽅或标注⼈员打分，重点关注⽣成内容是否符合语义、逻辑通顺、不胡说⼋道。像⽤Qwen或Llama微调后，常出现“套话连篇但答⾮所问”的问题，这种机器指标发现不了。

3）上线前必须⾛A/B测试。把⽼模型和新模型同时跑在线上，按流量切分，对⽐点击率、⽤户停留时⻓、转化率这些业务指标。⽐如在客服场景⽤微调模型，⽬标是降低⼈⼯转接率，那这个值下降 $10 \%$ 以上才叫真有效。

4）还得看泛化性。拿⼀些边缘case或分布外数据测试，⽐如新增的⽤户query类型，模型能不能兜住。如果⼀遇到没⻅过的句式就崩，说明过拟合了，得回炉加数据增强或者正则。

代码层⾯可以写个简单的评估脚本：

```python
from sklearn.metrics import f1_score  
f1 = f1_score(y_true, y_pred, average='weighted')  
print(f"微调后F1: {f1:.3f}")
```

最后记住，过拟合是微调最⼤的坑，训完训练集接近 $1 0 0 \%$ 准确率，验证集却卡在 $7 0 \%$ ，基本就是背答案了。数据质量差、样本太少、学习率太⾼都可能引发这问题。

# 介绍⼏种常⻅的微调策略的优缺点

微调⼤模型不是上来就全量参数⼀把梭，得看资源和场景做选择。

1）全量微调把所有参数放开训练，效果最好，像Llama系列在特定任务上刷榜基本都靠它。但代价也⼤，⼀张A100训个7B模型就得跑好⼏天，显存轻松⼲到80G以上，⼩团队根本搞不定。

2）LoRA（低秩适配）是现在最⽕的轻量⽅案。它冻结原模型，在输⼊层加两个低秩矩阵做增量，训练时只更新这两块。⽐如HuggingFace上很多基于Qwen、ChatGLM的衍⽣模型都是⽤LoRA微出来的。显存能压到20G内，训练快，还能多任务共⽤⼀个底模型。缺点是超参敏感，r秩选不好容易⽋拟合。

3）AdapterTuning在Transformer层中间插⼊⼩型神经⽹络模块，训练时只动这些⼩模块。结构改动⽐LoRA⼤，推理有延迟，但现在基本被LoRA吊打，除⾮你对模块化设计有强需求。

4）Prefix Tuning 和 Prompt Tuning 都是往输⼊前⾯塞可学习的向量。前者改 attention key/value，后者直接拼接embedding。适合少样本场景，但⻓序列下效果不稳定，⼀般只⽤于探索性实验。

⼀般来说，LoRA是平衡效果和成本的⾸选，真要拼上限再考虑全量。

向量数据库中，常⻅的向量搜索⽅法：余弦相似度、欧⼏⾥得距离和曼哈顿距离分别是什么？有什么区别？

向量搜索的本质是衡量两个向量之间的“距离”或“⽅向相似性”，不同度量⽅式适⽤于不同场景。

余弦相似度关注的是向量间的夹⻆，不关⼼⻓度。它把向量投影到单位球⾯上，算的是它们⽅向的⼀致性。值在-1到1 之间，越接近 1 表⽰⽅向越⼀致。适合⽂本、图像 embedding 这类语义匹配场景，⽐如⽤ Milvus 或 Faiss 做相似句⼦检索时，默认往往就是余弦相似。

欧⼏⾥得距离是两点间的直线距离，公式就是 $\sqrt { 2 } ( x \vert - y \vert ) ^ { 2 }$ 。它对向量的绝对位置敏感，适合特征空间中坐标准确反映实际差异的情况，⽐如地理坐标聚类。但⾼维下容易“维度诅咒”，距离都拉得很开，区分度下降。

曼哈顿距离是各维度绝对差之和，Σ|xi−yi|，也叫 L1 距离。它沿着坐标轴⾛“⽹格线”，对稀疏数据更鲁棒，计算也轻。在某些稀疏embedding或特征⼯程中会⽤到，不过在主流向量化检索系统中⽤得少。

1）余弦相似度看⽅向，适合语义匹配

2）欧⼏⾥得距离看直线远近，适合低维稠密空间

3）曼哈顿距离看⽹格步数，抗噪强但应⽤窄

选择哪种，得看数据分布和业务⽬标。⽐如推荐系统⾥⽤户向量归⼀化了，⽤余弦最稳；没归⼀化且维度不⾼，可以试试欧⽒。

向量A 余弦相似度 £ 夹角小则相似

向量C 欧几里得距离 £ 直线短则相近

向量E 曼哈顿距离 网格步数少则近

# 在RAG应⽤的过程中，关于提⽰⼯程的设计有什么⼼得和技巧吗？

提⽰⼯程在RAG（检索增强⽣成）⾥不是简单拼接问题和⽂档，⽽是决定模型能不能把检索到的内容⽤对、⽤好的关键。设计得好，⼤模型能像专家⼀样精准回答；设计得不好，结果可能张冠李戴。

# 1）上下⽂组织要有结构

别把⼀堆段落堆给模型。要把检索到的⽚段按相关性排序，加上来源标记，⽐如⽤ 【doc1】 开头标注。这样模型更容易分辨信息出处，减少混淆。

# 2）指令要明确约束输出⾏为

直接告诉模型“只基于提供的⽂档回答，不知道就说不知道”。避免它⾃由发挥。可以加⼀句：“如果信息不完整，请拒绝回答”，防⽌幻觉。

3）利⽤模板提升稳定性

预定义提⽰模板，固定⻆⾊、任务和格式。例如：

你是⼀个⾦融客服助⼿，请根据以下材料回答⽤户问题。回答要求：简洁准确，不超过 50 字，引⽤⽂档编号。

【doc1】中国2023年GDP增速为5.2%...【doc2】美联储2023年加息三次...

问题：2023年中国GDP增速是多少？回答：2023年中国GDP增速为 $1 5 . 2 \%$ 【doc1】

4）动态截断控制token⻓度

⻓⽂档容易撑爆上下⽂窗⼝。⼀般⽤BERTScore或最⼤边际相关性（MMR）做去重和精简，保留最相关的句⼦。HuggingFace 的 sentence-transformers 可以快速实现这⼀点。

5）加⼊推理引导提升逻辑性

对于复杂问题，可以在提⽰中引导分步思考。⽐如“先判断问题类型，再查找对应数据，最后组织语⾔”。

实际项⽬中，LangChain和LlamaIndex都提供了提⽰模板管理功能，⽀持动态注⼊检索结果，建议结合使⽤。持续A/B测试不同模板对准确率的影响，才是⻓期优化的关键。

# 什么是 Advanced RAG？

Advanced RAG 是在基础 RAG（Retrieval-Augmented Generation）之上，通过优化检索和⽣成两个环节的协同效率，提升回答质量的⼀套⽅法论。它不是某个具体⼯具，⽽是⼀系列增强技术的组合。

1）传统RAG通常直接⽤⽤户问题去向量库检索，但⾃然语⾔存在歧义或表述不清的问题，导致召回不准。AdvancedRAG会先做查询重写，⽐如⽤LLM把原始问题拆解成多个⼦问题，或者改写成更适合检索的关键词形式，像DPR（Dense Passage Retrieval）这类模型就常被⽤来做语义对⻬。

2）在检索阶段，除了单纯找top-k最相似的⽂档块，还会引⼊重排序（Re-Ranking）。⽐如⽤Cross-Encoder对初步召回的结果做精细打分，把真正相关的排前⾯。这块可以结合BM25等稀疏检索做混合召回，提升覆盖度。

3）⽣成环节也不再是“⼀把喂给LLM”。有些⽅案会做上下⽂压缩，只提取出与问题最相关的句⼦⽚段，减少噪声和token消耗。还有像Self-RAG这样的思路，让模型⾃⼰判断是否需要检索、要不要采纳检索结果，增加推理可控性。

代码上其实变化不⼤，核⼼是流程增强：

```txt
伪代码：Advanced RAG 流程  
rewritten_query = rewrite_prompt(user_query)  
docs = vector_store.search(rewritten_query, k=10)  
reranked_docs = crossEncoder_berank(rewritten_query, docs)  
context = compress_context(rewritten_query, reranked_docs)  
answer = lvm_generate(context, user_query)
```

整个链路更像是⼀个可调教的系统⼯程，典型应⽤有LangChain $^ +$ FAISS/BGE + Cohere Rerank 的组合，或者是⽤LlamaIndex做节点后处理。关键是要能根据业务场景动态调整各模块权重，⽽不是堆模块。

# 什么是 Modular RAG？

ModularRAG不是某个固定框架，⽽是指⼀种将RAG（检索增强⽣成）系统拆解成独⽴、可替换模块的设计思路。你完全可以把它看作RAG的“微服务化”⸺每个环节单独优化、灵活组合。

整个流程通常包括⼏个关键阶段：⾸先从外部知识库中检索相关⽂档，然后对检索结果做重排序（Rerank），最后把处理好的上下⽂喂给⼤模型⽣成答案。传统RAG把这些步骤耦合在⼀起，⽽ModularRAG强调每个部分都能独⽴迭代。

⽐如你在⽤LangChain或LlamaIndex时，可以⾃由替换不同的检索器（如从BM25切到向量检索）、换上Cross-Encoder 做精排、再接⼊不同的 prompt ⼯程策略。这种结构下，⼀个团队可以专注优化检索质量，另⼀个团队负责提升⽣成流畅度，互不⼲扰。

1）检索模块：⽀持多路召回，⽐如同时⾛关键词和语义向量2）重排序模块：⽤更精细的模型对Top-K结果打分，提升相关性3）上下⽂融合：对多个⽚段做去重、摘要或拼接，减少噪声4）⽣成控制：动态决定是否启⽤检索，避免“硬套答案”

这种⽅式特别适合复杂场景，像在企业知识库中查政策，可能需要结合时间过滤、权限判断等额外逻辑，直接塞进端到端RAG很难维护。拆成模块后，脏活累活交给对应组件，主链路反⽽更清晰。

# ComputerUse是什么？说说它的原理

⽬前没有明确的技术标准或⼴泛认知的系统叫做"ComputerUse"。这个术语在主流计算机科学、软件⼯程或IT基础设施领域并不指代某个具体的技术、协议或架构。

如果你指的是“计算机的使⽤”（theuseofcomputers），那涵盖范围⾮常⼴，包括操作系统调度、程序执⾏、内存管理、⽹络通信等基础⾏为。但作为⼀个专有名词，“ComputerUse”并不是像Redis、Kafka或JVM这样的具体技术组件。

有可能是提问时表述有误，⽐如本意想问的是：

ComputeUnit：计算单元，常⻅于分布式计算框架（如Spark中的executor）或硬件架构中。

Computer Vision：计算机视觉，AI 的⼀个分⽀。

Computer Cluster：计算机集群，⽤于⾼性能计算或服务扩容。

或者某个特定产品/项⽬中的内部命名，例如某系统的“ComputerUseService”类。

建议确认题⽬是否准确。如果是⾯试中遇到这个问题，可以先和⾯试官澄清概念，避免答偏。很多时候，这种模糊题是在考察你如何应对需求不明确的问题⸺这时候沟通能⼒和问题拆解能⼒⽐技术本⾝更重要。

与其纠结术语定义，不如展⽰分析思路：1）询问上下⽂场景

2）列举可能的相近概念进⾏排除

3）基于合理假设给出解答路径

这样反⽽更容易拿到⾼分。

# 在⼤模型应⽤中，通常如何实现⻓短期记忆机制？

⼤模型本⾝没有内置的⻓期记忆，每次对话都是独⽴的。要实现⻓短期记忆，得靠外部⼿段和架构设计来补⾜。

短期记忆⼀般通过上下⽂窗⼝管理。模型能处理的token数有限，⽐如32K，把最近的对话历史拼接进去就⾏。关键是怎么裁剪，别让上下⽂爆炸。常⻅的做法是滑动窗⼝、摘要压缩，或者⽤向量检索挑出最相关的⼏句历史，这样既

能保留关键信息，⼜不会超出⻓度限制。

⻓期记忆就得依赖外部存储了。⽤户的历史⾏为、偏好、重要事件这些数据，存到数据库⾥，⽐如⽤向量数据库存语义特征。每次新请求进来，先根据当前输⼊去检索最相关的历史⽚段，再把这些“记忆”注⼊ prompt。像LlamaIndex或LangChain这类框架，就提供了现成的记忆管理模块，⽀持会话级的状态保持。

状态同步也得考虑。如果应⽤是分布式的，会话状态不能只存在本地，得⽤Redis这种中间件做共享存储，保证每次请求都能拿到⼀致的历史。

说⽩了，模型只负责“想”，不负责“记”。所有记忆相关的脏活累活，都是外围系统在扛。

# Copilot 模式和 Agent 模式的区别是什么？

Copilot 模式和 Agent 模式代表了 AI 编程辅助的两种不同层级。

Copilot更像是⼀个实时建议者，你在写代码时它在旁边提供建议。你敲下⼀⾏，它预测下⼀⾏，⽐如在IntelliJ或VSCode ⾥补全⼀段⽅法体。它的响应延迟要求⾼，⼀般在 $2 0 0 \mathsf { m s }$ 内给出提⽰，决策链路短，不会⾃⼰发起动作。典型的场景是GitHubCopilot补全函数、⽣成单元测试。

Agent模式则更进⼀步，它能⾃主规划和执⾏任务。给你提个需求，⽐如“新建⼀个SpringBoot项⽬，集成MySQL和Redis”，它能拆解任务、创建⽂件、写配置、甚⾄跑通CI。整个过程不需要你⼀步步确认，它会⾃⼰调⽤⼯具、检查结果、修正错误。背后依赖的是LLM的推理能⼒加上外部⼯具链，⽐如LangChain或AutoGPT框架⽀持的插件系统。

关键区别在于控制权。Copilot等你触发，输出是建议；Agent⾃⼰决定下⼀步做什么，输出是完成的任务。

举个例⼦：

你写 // 查询⽤户订单 ，Copilot接着帮你写出SQL查询代码。

你说“把⽤户查询功能加上缓存”，Agent会分析现有代码，修改DAO层，加RedisTemplate调⽤，更新配置⽂件，还可能加上降级逻辑。

简单说，Copilot是副驾驶，Agent是⾃动驾驶。

# Agent智能体的⼯作过程是怎样的？

Agent智能体不是简单的问答机器⼈，它更像⼀个能⾃⼰“思考”并采取⾏动的⾃动化代理。整个过程围绕⽬标驱动，通过感知、决策、执⾏和反馈闭环来完成任务。

1）⾸先从环境或⽤户指令中获取输⼊，⽐如⼀段⽂字需求。接着进⾏规划，把⼤⽬标拆解成可执⾏的⼩步骤，这⼀步会⽤到提⽰⼯程⾥的思维链（Chain of Thought）或ReAct框架。

2）进⼊⼯具调⽤阶段，如果当前任务需要外部信息，⽐如查天⽓、发邮件或者搜索数据库，Agent就会选择合适的⼯具（Tool）发起调⽤。这个过程通常由LLM判断该不该⽤、⽤哪个，并⽣成符合格式的请求参数。

3）拿到⼯具返回结果后，再结合上下⽂做下⼀步推理，决定是继续调⽤其他⼯具还是直接⽣成最终回复。整个流程可以循环多次，直到达成⽬标。

代码层⾯⼀般基于LangChain或LlamaIndex这类框架搭建，它们提供了统⼀的Agent接⼝、Tool抽象和记忆管理机制。⽐如在LangChain⾥，你只需要定义好tools列表和llm实例，就能快速构建⼀个具备搜索 $^ { \dag + }$ 计算能⼒的Agent。

关键在于⾃主性和动态规划，不是预设流程，⽽是根据中间结果不断调整策略。但也要注意控制循环深度，避免陷⼊⽆限调⽤陷阱。

# LLM Agent 如何进⾏动态 API 调⽤？

LLMAgent做动态API调⽤，关键在于把⾃然语⾔意图转成结构化请求，中间靠⼯具抽象和运⾏时绑定撑起来。

Agent不是直接拼URL调接⼝，⽽是通过定义好的⼯具描述（ToolDescription），让模型知道“我能⼲啥”。⽐如你接⼊了⻜书消息 API 或内部⼯单系统，就封装成 tool，带上 name、description、parameters，⽤ JSON Schema 描述输⼊格式。模型输出会明确说“我要⽤send_message这个⼯具，参数是 $\tan =$ 张三,content=上线提醒”，⽽不是⾃由发挥写⼀段话。

真正执⾏时，Agent框架捕获这个调⽤意图，拿参数去实例化真实请求。这块⼀般有统⼀的ToolExecutor，注册所有可⽤⼯具，做参数校验、鉴权、重试，再发出去。像LangChain、LlamaIndex都是这么搞的，你⾃⼰写也建议拆成两层：⼀层对⻬模型理解，⼀层处理HTTP、序列化这些脏活累活。

代码上⼤概⻓这样：

```java
record SendMsgTool(@NonNull String to, @NonNull String content) implements Tool { public void run() { // 实际调飞书 WebhookHttpClient.newCall(req -> req.url("https://open.feishu.cn/path") .postjson(to, content)); } }
```

整个流程其实是“模型提议 $^ +$ 系统执⾏”的分离设计。模型压根不经过⽹络层，只负责决策调哪个⼯具；真正的API调⽤由运⾏时安全落地，避免幻觉乱发请求。⾼频场景⽐如⾃动查数据库、触发CI/CD、拉取监控指标，都是靠这套机制扛住的。

# LangChain 的核⼼组件有哪些？

LangChain的设计是为了解耦⼤模型应⽤的各个关键环节，让开发者能灵活组装。它不是单⼀⼯具，⽽是⼀套拼图。

# 1）Model I/O

负责与⼤模型交互，封装了输⼊输出逻辑。⽀持多种模型类型，⽐如 OpenAI、Anthropic、Hugging Face 等。你不⽤⾃⼰写HTTP请求，它帮你统⼀调⽤⽅式。

# 2）Prompts

提⽰词管理模块，包括提⽰词模板（PromptTemplate）和⽰例选择器（ExampleSelector）。你可以定义变量化的prompt，⽐如把⽤户问题动态填⼊模板，还能做few-shot⽰例注⼊。

# 3）Chains

把多个步骤串起来执⾏。⽐如先调⽤模型⽣成摘要，再⽤另⼀个prompt做情感分析，整个流程封装成⼀个chain。最常⽤的是 LLMChain ，也可以⾃定义复杂链式逻辑。

# 4）Agents

允许模型“决策”下⼀步动作。⽐如模型判断当前需要查天⽓，就会调⽤指定⼯具（Tool），执⾏完再继续推理。背后依赖 Tools 和 AgentExecutor，典型场景像 LangChain 结合 SerpAPI 做搜索代理。

# 5）Memory

维持对话状态，常⻅有 ConversationBufferMemory （保存全部历史）和 ConversationSummaryMemory（只存摘要）。适合聊天机器⼈这类需要上下⽂记忆的应⽤。

# 6）Retrieval

结合向量数据库做检索增强。⽐如⽤FAISS或Chroma存⽂档嵌⼊，查询时先检索相关⽚段，再喂给模型⽣成答案，有效缓解幻觉。

这些组件可以单独使⽤，也能组合出复杂应⽤，关键是按需选取，别⼀上来就全堆上去。

# LangChain核⼼架构是什么样的

LangChain的设计其实围绕⼀个核⼼⽬标：让⼤模型能像搭积⽊⼀样灵活接⼊各种外部能⼒。它不追求把所有功能塞进引擎，⽽是通过标准化接⼝降低扩展成本。

链（Chain）是整个架构的组织单元，你可以把多个处理步骤串成⼀条流⽔线。⽐如先⽤PromptTemplate⽣成⽂本，再交给LLM处理，最后调⽤API写⼊数据库，每个环节都是可替换的组件。

关键抽象有四个： 1）Model I/O 封装了⼤模型的输⼊输出，⽀持 OpenAI、Anthropic、HuggingFace 等主流服务 2）Retriever负责从外部获取数据，典型的是⽤FAISS或Chroma做向量检索3）Tool允许模型调⽤外部函数，⽐如搜索天⽓、执⾏ Python 代码 4）Agent 根据 prompt 决定调⽤哪些 Tool，实现动态决策流

实际项⽬⾥，你常会看到Agent结合ReAct模式⼯作。模型输出带特殊标记的⽂本，框架解析后触发⼯具调⽤，结果再拼回去继续推理。这种设计让逻辑闭环可以在⼀次会话中反复迭代。

和直接调API的最⼤区别是，LangChain把“感知-决策-⾏动”循环变成了可配置的⼯作流。但要注意，链路越⻓，延迟叠加越明显，调试也越困难。简单任务直接⽤LLMClient反⽽更稳。

# 什么是A2A协议，它的核⼼架构及主要组件有哪些？

A2A（Application-to-Application）协议不是某个具体的技术标准，⽽是描述系统间通过预定义接⼝直接通信的模式。这类交互通常在服务之间完成数据交换或功能调⽤，不依赖⽤户参与。

⼀般架构下，A2A的核⼼是去中⼼化或轻量⽹关控制的服务直连。常⻅于微服务、B2B集成或内部系统协同场景。⽐如订单系统⾃动触发库存扣减，就是典型的A2A调⽤。

典型组件包括：

1）服务提供⽅：暴露RESTfulAPI或gRPC接⼝，⽐如⽤SpringBoot实现的⽤户中⼼服务。2）服务消费⽅：主动发起请求的应⽤，例如交易系统调⽤⻛控服务做决策。3）认证与授权模块：常⽤OAuth2的ClientCredentials模式，确保机器⾝份可信。API密钥也常⽤于轻量场景。4）API⽹关（可选）：像Kong或Apigee，负责限流、⽇志、路由，但⾼并发内⽹调⽤时常绕过⽹关直连以降低延迟。5）服务注册与发现：在动态环境中，Eureka或Nacos帮助消费⽅找到可⽤实例。

代码上，⼀个简单的A2A调⽤可能⻓这样：

```javascript
// 使用HttpClient发起异步请求  
webClient.get()  
    .uri("http://user-service/users/123")  
    .retrieve()  
    .bodyToMono(User.class)  
    .block();
```

注意点在于⽹络超时、重试策略和熔断机制。如果搞不定容错，雪崩效应会迅速扩散。因此，配合Hystrix或Resilience4j 是常规操作。

# A2A协议有哪五⼤设计原则？

A2A（Application-to-Application）协议本质是服务间通信的契约设计，重点在于稳定、⾼效、可维护。它的五⼤设计原则其实围绕的是“解耦”和“可控”。

# 1）接⼝版本化

接⼝⼀旦发布就不能随便改，否则上游调⽤⽅会炸。⼀般通过URL路径或Header携带版本信息，⽐如 /v1/order和 /v2/order 并⾏存在，⽼接⼝逐步下线。

# 2）明确的契约定义

⽤OpenAPI（Swagger）、Protobuf或Thrift明确定义输⼊输出结构，字段类型、是否必填、枚举值都要说清楚。前后端或跨团队协作时，契约先⾏，避免“我猜你返回的是个字符串”。

# 3）错误码标准化

别随便返回200包着⼀个 {code: 500} 的体。HTTP状态码要合理使⽤，业务错误码要统⼀规范，⽐如ORDER_NOT_FOUND=10001 ，⽂档可查，⽇志可追踪。

# 4）限流与熔断机制内建

系统扛不住的时候得⾃我保护。A2A调⽤必须内置限流（如令牌桶）和熔断（如Hystrix、Sentinel），防⽌雪崩。⽐如下单服务被查询服务拖垮，就得把⾮核⼼链路熔断掉。

# 5）可观测性⽀持

每⼀次调⽤都得能追踪，通过链路追踪系统（如SkyWalking、Zipkin）记录请求路径，结合⽇志和监控指标（延迟、QPS），快速定位问题在哪⼀环。

# A2A协议与MCP协议的关系是怎样的？

A2A和MCP都是服务间通信的协议⽅案，但定位和层级不⼀样。

A2A ⼀般指 Application-to-Application，是业务应⽤之间的直接调⽤协议，⽐如通过 Dubbo、Spring Cloud RPC 或gRPC实现。这类调⽤压根不经过⻚⾯层，都是接⼝对接⼝，常⻅于微服务架构⾥订单系统调库存系统这种场景。

MCP全称可能是ModuleCommunicationProtocol，但在阿⾥系中间件语境下，它更多指⼀种模块级通信规范，通常运⾏在同⼀个应⽤内部的不同逻辑模块之间，或者是轻量级跨进程通信的封装。它的抽象层级⽐A2A低⼀些，更像是中间件内部组件交互的语⾔。

你可以把A2A看作城市之间的⾼速公路，两个独⽴城市（应⽤）之间跑整⻋货（请求体）。⽽MCP更像是⼀个⼯⼚内部的传送带，不同⻋间（模块）之间传递零件，节奏更紧凑，协议更定制化。

提⽰词优化考虑哪些维度？你们提⽰词模板有哪些字段？

这问题其实是在问提⽰词⼯程的系统化设计思路，不只是随便写句话。

1）⾸先看维度。⼀个有效的提⽰词必须明确任务⽬标、输⼊约束和输出格式。任务类型决定结构，⽐如分类、⽣成、抽取需要的模板完全不同。上下⽂信息也得给⾜，模型才能理解语义边界。还要考虑安全合规要求，像敏感词过滤、价值观对⻬这些都得前置控制。

2）再说模板字段。我们常⽤的提⽰词模板包含这⼏个关键部分：⻆⾊定义，说明这个prompt是给谁⽤的；背景描述，交代清楚业务场景；指令主体，这是核⼼，告诉模型具体要做什么；⽰例样本，few-shot的例⼦能显著提升准确率；输出约束，⽐如JSON格式、字数限制、枚举值范围；最后是异常处理机制，定义模糊输⼊时的降级策略。

代码⽰例⻓这样：

prompt $=$ ""  
角色：电商客服助手  
背景：用户在商品详情页发起咨询  
指令：根据商品信息和用户问题，生成专业且友好的回复  
输入：-商品标题：{title}  
-用户问题：{query}  
输出格式：JSON，包含reply字段，不超过150字

这种结构能让⼤模型稳定输出符合预期的结果，⽽不是靠运⽓。

# 你有多个知识库，做RAG的时候，怎么保证查询效率和准确性兼容，并尽可能减少幻觉？

多个知识库做RAG，关键是在检索阶段就控制好数据的“来源质量”和“语义相关性”，否则后⾯⽣成再怎么优化也压根不经过。

1）先做知识库的预分类或打标。⽐如⽤Milvus或Elasticsearch存向量时，给每个⽂档加metadata标记来源类型（如产品⽂档、客服记录、API⼿册）。查询时先根据query的意图路由到最可能相关的库，避免全量检索拖慢速度。

2）⽤混合检索策略。单纯靠向量可能召回语义相近但事实错误的内容，容易引发幻觉。结合关键词匹配（BM25）和向量相似度，像Weaviate或Vespa都⽀持这种hybridsearch，能同时抓住字⾯匹配和深层语义，准确率提升明显。

3）检索后做重排序（rerank）。别拿到top-k就直接喂给LLM，⽤⼀个轻量级模型⽐如BGE-reranker对结果按相关性重新打分，把真正靠谱的段落往前排。这⼀步能过滤掉不少“看起来像对其实不对”的内容。

4）在prompt中显式标注信息来源。把检索到的⽂本块加上出处标签，⽐如[来⾃：API⼿册v3.2]，让⼤模型知道依据从哪来，⽣成时更倾向引⽤原⽂，减少脑补。

5）最后加⼀层验证机制。对关键回答，可以⽤⼩模型做⼀致性校验，⽐如把⽣成结果和原始⽂档⽚段做⼀次entailment判断，不⼀致就触发⼈⼯审核或fallback回答。

Agent死循环问题有遇到过吗？如何解决？

Agent死循环通常发⽣在字节码增强逻辑⾥，⽐如⽤JavaAgent做监控或APM时，不⼩⼼把⾃⼰instrument的类⼜触发了新的 transform，结果⽆限加载 class，CPU 直接打满。

最常⻅的场景是，你在 ClassFileTransformer ⾥处理某个类的时候，执⾏了某些代码，这些代码⼜动态⽣成类或者触发类加载，⽽你的transformer没做过滤，就会重新进⼊transform⽅法，形成递归调⽤。特别是⽤到ASM、CGLIB、Javassist 这些框架时很容易中招。

解决办法其实就两条：

如果⼀个GPU集群的LLM处理能⼒为1000tokens/s，那1000个⽤户同时并发访问，响应给每个⽤户的性能只有1 token/s吗？怎么分析性能瓶颈

不⼀定每个⽤户就只能分到1token/s，实际性能取决于调度策略、批处理能⼒和请求的负载特征。

⼤模型服务不像传统Web服务器那样“⼀个请求占⼀个线程”，它⾛的是动态批处理（DynamicBatching）路⼦。⽐如⽤vLLM、TensorRT-LLM这类推理框架时，多个⽤户的请求会被合并成⼀个batch⼀起跑，显存和计算单元利⽤率更⾼。

关键点在于：

1）如果这1000个⽤户都是刚发请求，还没开始⽣成内容（prefill阶段为主），那系统可以⼀次性把他们的prompt做batch处理，吞吐可能接近峰值1000tokens/s，平均下来每⼈⼏⼗甚⾄上百token/s都有可能。

2）但到了 decode 阶段，每个请求要逐 token ⽣成，且⻓度不⼀，这时候 batch size 会慢慢被“拖慢”。⻓⽂本、⾼采样参数（如temperature⾼）的请求会拉低整体速度。

3）真正的瓶颈往往不是算⼒，⽽是显存带宽和KVCache管理。每个并发请求都要保留KVCache，1000个并发意味着巨⼤的显存压⼒，搞不定就会OOM或被迫丢请求。

举个例⼦，A100显存80GB，跑Llama3-8B，每个请求平均占2GBKVCache，理论上最多撑40个并发。超过就得靠PagedAttention（像vLLM实现的）来分⻚管理，否则压根不经过计算就挂了。

所以性能瓶颈通常出现在：

KV Cache 显存占⽤过⼤

⼩ batch 或不规则请求导致 GPU 利⽤率上不去

请求排队时间远超⽣成时间

优化⽅向是：⽤PagedAttention降低显存压⼒，启⽤连续批处理（ContinuousBatching），控制最⼤⽣成⻓度，避免⼩请求拖垮整体延迟。

什么是低秩适配（LoRA）技术？如何结合LoRA技术进⾏微调？

低秩适配（LoRA）的核⼼思路是，⼤模型微调时参数量太⼤，训练慢、显存吃紧，⼲脆不直接改原始权重，⽽是⽤低秩矩阵去近似增量。

模型原本的权重矩阵$W$是个⼤胖⼦，⽐如 $7 6 8 \times 7 6 8 _ { \circ }$ 。LoRA不动它，转⽽引⼊两个⼩矩阵$A$和$B$，维度分别是$\$ 768\times r5$ 和 $\$ 123,45$ ，其中 $\$ 1$ 很⼩，⼀般取8到64。训练时只更新这两个⼩矩阵，前向传播时等效注⼊$\DeltaW= A \times B$。

这样显存和计算量就从和原矩阵成正⽐，变成和 $\$ 1$ 相关。⽐如 $\mathsf { r } { = } 8$ ，参数量直接降到原来的1/96，训练速度翻倍都不⽌。

结合LoRA做微调，流程也简单：

1）冻结原始模型所有权重

2）在指定层（⽐如注意⼒中的 Q、V 投影）插⼊ LoRA 模块

3）只训练新增的⼩矩阵，其余参数不动

4）推理时把 $A \times B$ 加到原权重上，或者直接合并进原权重

主流框架都有⽀持。HuggingFace的 peft 库⼏⾏代码就能上：

```python
from peft import LoraConfig, get_peft_model  
lora_config = LoraConfig( r=8, lora_alpha=16, target Modules=['q_proj', "v_proj'], lora_dropout=0.1, bias="none", task_type="CAUSAL_LM")  
model = get_peft_model(model, lora_config) 
```

适合资源有限、多任务切换的场景。像微调⼀个7B模型，⽤LoRA能在单卡24G显存下搞定，否则根本搞不定。

# 微调的过拟合⻛险如何通过正则化缓解？

微调时模型已经⻅过⼤量训练数据，参数调整幅度⼩但密集，容易记住训练集的特定模式，导致在新数据上表现下滑。正则化的核⼼作⽤就是在损失函数或训练过程中加⼊约束，让模型别学得太“死”。

1）L2正则（权重衰减）是最常⽤的⼿段。它在损失函数⾥加上所有权重的平⽅和，迫使参数值趋向更⼩。⽐如Hugging Face 的 Trainer ⾥设置 weight_decay=0.01 ，就能防⽌某些权重变得过⼤，提升泛化能⼒。

```python
training_args = TrainingArguments( output_dir="output", weight Decay=0.01 
```

2）Dropout在微调阶段依然有效。虽然预训练模型内部已经固化了结构，但在分类头甚⾄最后⼏层中间加Dropout，能让输出不依赖于少数神经元。⼀般保留率设在 $0 . 1 { \sim } 0 . 3$ 就够了。

3）早停（EarlyStopping）特别适合微调场景。因为微调轮次少，可能只跑 $3 { \sim } 5$ 个epoch，验证集性能⼀旦下降就终⽌，能避免多⾛⼀两步掉进过拟合坑⾥。

4）还有像标签平滑（LabelSmoothing）这种软化监督信号的⽅法。它不让模型对真实标签过于⾃信，间接抑制过拟合。在分类任务中设 label_smoothing_facto $\mathsf { r } { = } \Theta \cdot 1$ 是常⻅做法。

这些⽅法本质都是给学习过程加点“不确定性”或“惩罚”，让模型别把微调当背书，稍微收着点劲。

# 请详细讨论微调时如何防⽌灾难性遗忘问题？

微调⼤模型时，灾难性遗忘的本质是模型参数被新任务数据剧烈调整，导致旧知识的表征能⼒崩塌。关键不是“记住所有旧数据”，⽽是让模型在适应新任务的同时，保留对原始分布的泛化能⼒。

1）降低学习率是最直接的⼿段。预训练阶段⽤了海量数据，参数已经收敛到⼀个较优的全局位置。微调时如果⽤⼤学习率，梯度更新会把参数推出这个区域。⼀般建议微调学习率设为预训练的1/10到1/100，⽐如从3e-4降到3e-5或1e-5。

2）使⽤Adapter模块是⼀种参数隔离策略。只在Transformer层间插⼊⼩型神经⽹络，冻结原始主⼲参数。训练时梯度只流经这些⼩模块，主⼲权重压根不更新。这样既适配了新任务，⼜完全保留了原模型的知识结构。HuggingFace 的 PEFT 库就⽀持这类⽅法。

3）LoRA（低秩适应）更轻量。它不加新层，⽽是给注意⼒权重矩阵注⼊低秩分解矩阵。假设原始权重是W，训练的是 $\Delta W = \mathsf { B A }$ （A∈R^{r×d}, ${ \mathsf { B } } { \in } { \mathsf { R } } ^ { \wedge } \{ { \mathsf { d } } \times { \mathsf { r } } \} )$ ），r远⼩于d（⽐如 $\mathord { \uparrow } = 8$ , $d = 4 0 9 6$ ）。更新时 $W ^ { \prime } = W + \alpha ^ { \star } \mathsf { B A }$ A，主⼲参数不变，只训练A和 $\scriptstyle \mathsf { B } _ { \circ }$ 。这种⽅法显存占⽤少，推理还能合并权重，适合⼤规模部署。

4）数据层⾯可以混合⼀定⽐例的通⽤语料。⽐如每10个微调样本中加⼊1个来⾃原始预训练分布的句⼦，让梯度⽅向不⾄于完全偏离。不过要⼩⼼引⼊噪声影响⽬标任务效果。

这些⽅法的核⼼思想都是限制参数搜索空间，不让优化过程肆意修改已学好的特征提取器。

# 在多模态微调（如图⽂⽣成）中，如何确保⽂本和图像数据的对⻬质量？

多模态微调⾥，⽂本和图像的对⻬质量直接决定模型能不能准确理解“图在说什么，话在描述谁”。如果数据没对⻬，模型学到的就是错配关系，⽐如把“猫坐在沙发上”跟⼀张狗的照⽚强⾏关联，后续⽣成或推理全崩。

1）⾸先靠⾼质量数据清洗。原始图⽂对往往来⾃⽹⻚，alt-text和图⽚内容不⼀致太常⻅。可以⽤预训练的CLIP模型做初筛，计算图⽂相似度，低于阈值（⽐如0.2）的直接过滤。CLIP本⾝是跨模态编码器，能给出语义匹配分数，这⼀步能⼲掉明显噪声。

2）然后是增强对⻬信号。单纯⽤原始图⽂对微调，监督信号弱。可以在输⼊侧构造负样本，⽐如同⼀个batch⾥拿其他样本的⽂本当负例，做对⽐学习（ITCloss），逼模型分辨“哪个⽂本真配这张图”。BLIP、ALBEF这些模型就这么⼲的。

3）微调策略上，不要只微调分类头，要端到端微调图像编码器和⽂本编码器。尤其是ViT的⾼层特征和⽂本token要能cross-attention对上。可以⽤attention可视化检查：⽣成⽂本时，模型是不是真的关注图中对应区域。

4）最后加点⽣成式损失，⽐如在decoder阶段⽤语⾔模型⽬标重建描述，让模型不仅判别还得会说。这样双重约束，对⻬更稳。

# 参数⾼效微调（PEFT）如何减少计算成本？

参数⾼效微调的核⼼思路是，不碰预训练模型的⼤部分权重，只动其中⼀⼩撮关键参数。这样⼀来，显存占⽤和计算量都⼤幅下降。

1）冻结主⼲：把⼤模型的绝⼤多数参数锁死，⽐如LLaMA的70亿参数⾥，可能只放开不到 $1 \%$ 去更新。剩下的全当静态特征提取器⽤。

2）引⼊可训练模块：像LoRA这种⽅法，会在注意⼒层的权重旁加个低秩矩阵做增量。训练时只优化这个⼩矩阵，原始权重压根不参与梯度更新。假设原矩阵是 $ \mathbb{R}^{5120 \times 5120} $，LoRA 只学两个 $\mathbb{R}^{5120 \times 8} $ 的⼩矩阵，参数量从千万级⼲到⼏万。

3）适配器注⼊：在Transformer层之间塞个⼩的前馈⽹络模块，叫Adapter。它通常就⼀两层，宽度也⼩，训练时只调这部分，其他照旧。像 BERT 这类模型⽤ Adapter 微调，能省下 $7 0 \%$ 以上的训练资源。

4）前缀微调：给输⼊前⾯挂⼀串可学习的虚拟token，叫prefix。训练时只更新这些token的embedding，模型主体完全不动。T5、GPT这类⾃回归模型常⽤这招。

这些⽅法都能做到单卡微调⼤模型。⽐如⽤LoRA调LLaMA-2-13B，在A100上也能跑起来，显存直接从⼏⼗GB掉到10G 内。

# 冻结层在微调中的作⽤是什么？

冻结层在微调时，其实就是把预训练模型⾥的⼀部分⽹络参数固定住，不让它们更新。你只让最后⼏层或者指定的层去学习新任务的数据，这样能省下⼤量计算资源。

1）最常⻅的情况是⽤BERT、ResNet这类⼤模型做下游任务。⽐如你拿ImageNet上训好的ResNet50去做猫狗分类，前⾯的卷积层已经学到了边缘、纹理这些通⽤特征，压根不需要重学。把这些层冻住，只微调最后的全连接层，⼏⼗个epoch就能收敛，显存和时间都扛得住。

2）另⼀个关键是防⽌过拟合。你的⼩数据集可能就⼏千张图，如果放开所有层去更新，模型很容易记住噪声，泛化能⼒直接崩掉。冻结⼤部分层相当于限制模型容量，逼它只调整⾼层语义适配新任务。

3）也有分阶段微调的做法：先冻结主⼲训 head，再解冻部分层⽤更⼩学习率细调。像 Hugging Face 的Transformers 库⾥， .requires_grad_() 控制起来也就⼀⾏代码的事。

#冻结BERTbase层  
model $=$ BertForSequenceClassification.from_pretrained('bert-base-uncased')  
for param in model.bert.params():paramrequires_grad $=$ False #梯度不计算，节省内存

这种策略在NLP和CV⾥都成了标配，尤其是数据少、⼜想⽤⼤模型的时候，基本靠它稳住局⾯。

# 为什么需要混合精度训练？

混合精度训练解决的是深度学习训练中的计算效率与显存占⽤问题。现代GPU如A100、V100都配备了TensorCore，专⻔为半精度浮点数（FP16）运算优化，单次可处理更多数据，算得更快。

1）FP16相⽐FP32占⽤带宽和显存少⼀半，同样的batchsize能跑更⼩的显存，或者在显存不变时增⼤batchsize提升训练稳定性。

2）但全⽤FP16会出问题，⽐如梯度下溢、权重更新精度不够导致模型不收敛。所以得保留⼀部分关键计算⽤FP32，⽐如梯度累加、权重更新、loss缩放。

3）实际做法是：前向和反向传播⽤FP16加速，参数副本保持⼀份FP32的主拷⻉⽤于更新，这就是AMP（AutomaticMixed Precision） 的核⼼机制。PyTorch⾥⼀⾏ scaler $=$ torch.cuda.amp.GradScaler() 就能开启。

像BERT、ResNet这类⼤模型训练，基本都默认开启混合精度。NVIDIA的Apex库和原⽣AMP都⽀持得很好。不⽤的话，等于⽩⽩浪费 $3 0 \%$ 以上的训练速度。

# 模型输出重复和幻觉如何微调解决？

模型输出重复和幻觉，本质是训练数据、⽣成策略和微调⽅式共同作⽤的结果。想靠微调彻底解决不现实，但能显著缓解。

1）重复问题，常⻅于解码阶段贪⼼搜索。beamsearch如果宽度太⼩，容易陷⼊循环。可以在推理时引⼊n-gram重复惩罚，⽐如 Hugging Face 的 transformers 库⾥设置 no_repeat_ngram_size=2 ，让模型避开已⽣成的词组。微调时也可以在loss上做⽂章，对重复token加权惩罚。

2）幻觉更棘⼿，模型把参数⾥的统计规律当事实输出。指令微调（InstructionTuning）是个办法，⽤⾼质量问答对训练，⽐如Alpaca数据集格式，教会模型“不知道就说不知道”。关键是数据质量，10万条精准样本⽐100万条噪声数据管⽤得多。

3）RLHF也能压幻觉，InstructGPT就这么⼲的。⽤⼈类偏好打标数据训练奖励模型，再⽤PPO调整⽣成策略，让输出更可信。但这套流程成本⾼，⼀般公司搞不定。

代码上，Hugging Face 的 Trainer 配合 DataCollatorForLanguageModeling 做微调很顺⼿。推理时控制top_p （0.9）和 temperature （0.7），别让模型太放⻜。

说到底，微调能改善，但没法根治。⼯程上得配合检索增强（RAG），让模型查实时数据，⽽不是全靠记忆。

# SFT指令微调数据如何构建？

SFT（SupervisedFine-Tuning）指令微调数据的构建，本质是把模型要学的任务表达成“指令-输⼊-输出”的三元组结构。关键不是堆数据量，⽽是让样本覆盖多样任务类型和表达⽅式。

1）⼀条标准样本包含三个部分：instruction是具体任务描述，⽐如“翻译成英⽂”；input是待处理内容，可以为空；output 是期望的模型输出。例如 instruction="摘要⽣成"，input="⼀段新闻⽂本"，output="⽣成的简短摘要"。

2）数据来源主要有⼏种路径。可以⽤公开指令数据集如Alpaca、Flan-v2做基础，再结合业务场景构造垂直领域样本。⽐如客服场景，收集真实⽤户问题和⼈⼯回复对，包装成指令格式。也可以⽤⼤模型⾃动⽣成指令样本，通过prompt 让 GPT-4 产出“问题 $\vdots +$ 答案 $\vdots +$ 上下⽂”，控制多样性和质量。

3）质量⽐数量重要。避免重复、歧义或错误标注。建议做分层设计：通⽤能⼒、领域知识、业务特有逻辑各占⼀定⽐例。⼀般⼏千到⼏万条⾼质量样本就能起效，上百万条反⽽可能引⼊噪声。

4）最后要做格式归⼀和去重。统⼀prompt模板⻛格，过滤低信息密度样本，⽐如全是停⽤词或模板化回复的数据。整个过程其实是为模型“造考场”，题⽬得能考出真本事。

# 指令微调的好处？

指令微调其实是让预训练模型更会“听⼈话”的关键⼀步。模型在⼤规模数据上预训练完，虽然学到了丰富的语⾔知识，但并不清楚⽤户到底想让它⼲什么。这时候通过指令微调，⽤成对的“指令-期望输出”数据去微调，它就能学会理解任务意图。

1）模型能准确理解任务形式。⽐如给⼀条指令“把下⾯这句话翻译成英⽂”，模型知道接下来要处理的是翻译，⽽不是摘要或改写。这种泛化能⼒在多任务场景下特别有⽤。

2）减少对⽰例的依赖。没有指令微调的模型，往往需要上下⽂⾥给出⼏个例⼦（few-shot）才能⼲活，⽽微调后的模型可以直接响应指令，输⼊更简洁。

3）⾏为更可控。你可以通过微调引导模型输出特定格式，⽐如JSON、有序列表，或者避免⽣成某些敏感内容。像Alpaca、Dolly这些开源模型，都是基于LLaMA做了指令微调才变得可⽤。

举个简单例⼦，微调前你问“写个快排”，它可能只解释原理；微调后它⼤概率直接给你⼀段可运⾏的代码。

不过也别指望它能完全替代⼯程逻辑。指令微调解决的是“意图对⻬”，不是“能⼒增强”。模型本⾝不具备的能⼒，⽐如数学推理、代码执⾏，光靠指令微调是搞不定的。

# 如何让LLMAgent具备⻓期记忆能⼒？

让LLMAgent有⻓期记忆，关键不是靠模型本⾝记住东西，⼤模型的上下⽂窗⼝再⼤，也就⼏⼗k到百ktoken，根本存不下⻓期数据。真正的解法是外挂存储 $^ +$ 检索机制。

1）把Agent历史交互、关键决策、⽤户偏好这些信息存到外部数据库。可以⽤向量数据库⽐如Chroma、Pinecone存语义向量，⽅便后续语义检索。同时⽤传统数据库如PostgreSQL存结构化元数据，⽐如时间、对话ID、标签等。

2）每次新请求进来，先根据当前输⼊做语义匹配，在向量库中查最相关的⼏段历史记录。这个过程叫Retrieval-Augmented Generation（RAG），把查到的内容拼进 prompt，⼀起喂给 LLM。

3）检索策略要设计好。不能每次都拉全部历史，会炸上下⽂。可以按时间衰减加权，或者⽤摘要压缩⽼记忆，⽐如每天⽣成⼀个当⽇⾏为摘要存进去。

// 伪代码⽰意：记忆检索核⼼逻辑

```txt
List<Memory> recent = memoryStore.findByTimeRange(last24Hours);  
List<Memory> relevant = vectorDB.similaritySearch(currentInput, topK=3);  
Prompt prompt = buildPromptWithMemories(currentInput, recent, relevant);  
String response = lvm_generate(prompt);  
memoryStore.save(new Memory(timestamp, currentInput, response)); // 写回
```

这么⼀来，Agent就能“记得”⼏个⽉前的事，还能理解“上次你说不喜欢红⾊”这种指代。本质上，⻓期记忆是个读多写少的系统，重点在快速定位有⽤信息，⽽不是全量回放。

# LLMAgent在多模态任务中如何执⾏推理？

多模态任务⾥，LLMAgent的推理不是简单看图说话，⽽是把⽂本、图像、⾳频这些不同模态的信息统⼀拉到⼀个向量空间⾥做对⻬。模型在预训练阶段就⻅过⼤量图⽂对，⽐如⽤CLIP这类结构把图⽚和⽂字映射到同⼀语义空间，这样⼀张“狗追球”的图，能和对应描述在特征上挨得特别近。

1）输⼊进来时，图像⾛视觉编码器（⽐如 ViT）转成 patch embeddings，⽂本⾛ tokenizer 转成 tokenembeddings，两者⻓度不⼀样没关系，关键是通过交叉注意⼒让LLM主⼲能“看⻅”图像特征。2）推理过程中，LLM不是只靠记忆⽣成答案，⽽是结合上下⽂做因果推断。⽐如问“图中动物在⼲什么”，它会关联“奔跑”、“草地”、“球体运动轨迹”这些视觉线索，⽣成“狗在追球”⽽不是“狗在睡觉”。3）有些复杂任务还会引⼊外部⼯具调⽤，⽐如先识别图像中的数学公式，再丢给SymPy计算，最后把结果整合进回答⸺这步就是agent的规划能⼒体现。

这类系统典型代表是LLaVA、Qwen-VL，它们在架构上做了端到端训练，确保语⾔模型能真正理解⽽不是“猜”图像内容。纯prompt⼯程压根搞不定跨模态语义鸿沟，必须依赖对⻬训练。

# LlamaIndex 如何与 LangChain 结合？

LlamaIndex和LangChain不是⼆选⼀的关系，更多时候是配合使⽤，⼀个搞数据连接，⼀个做流程编排。

1）LlamaIndex的核⼼是索引。它擅⻓把⾮结构化数据⽐如PDF、数据库、⽹⻚内容，变成向量或结构化索引，⽅便⼤模型⾼效检索。像你⽤它接Notion、Slack数据，做RAG（检索增强⽣成），效果很直接。

2）LangChain重点在链式流程。你要串起提⽰词、⼯具调⽤、记忆管理、多个LLM步骤，LangChain提供了统⼀的抽象和调度能⼒。⽐如你做⼀个客服机器⼈，要先查订单，再⽣成回复，还得记住上下⽂，这就得靠 Chain 或 Agent模式。

它们怎么结合？常⻅两种⽅式：

第⼀种，⽤ LlamaIndex 做数据源，喂给 LangChain 流程。⽐如你在 LangChain ⾥定义⼀个 RetrievalQA 链，retriever 直接对接 LlamaIndex 构建的 VectorStoreIndex。

第⼆种，反过来，在 LlamaIndex 的 Query Engine ⾥嵌⼊ LangChain 的组件。⽐如你让 LlamaIndex 查完数据后，⽤ LangChain 的提⽰模板重写查询，或者调⽤外部 API 补充信息。

![image](https://cdn-mineru.openxlab.org.cn/result/2026-04-10/a4546dd9-d3cc-4d94-90fb-a52fb3050fc3/27229e5e9953d87db4237f9c28e828bd836b3a75fc3c3f6b85c60e1c83f73fc0.jpg)


简单说，LlamaIndex解决“从哪找数据”，LangChain解决“怎么⼀步步处理”。⼀个负责精准拉取，⼀个负责逻辑流转，搭在⼀起能快速做出复杂应⽤。

# AutoGPT如何实现⾃主决策？

AutoGPT本⾝并不是⼀个标准化的开源框架，⽽是⼀类基于⼤语⾔模型（LLM）实现⾃主任务分解与执⾏的实验性系统。它的“⾃主决策”能⼒，其实是通过提⽰⼯程 $^ +$ 外部⼯具调⽤ $^ +$ 反馈循环构建出来的⾏为模式。

1）它的核⼼机制是把⽬标输⼊给LLM，让模型⾃⼰拆解成可执⾏的⼦任务。⽐如你要它“开发⼀个待办事项应⽤”，它会先决定需要创建项⽬⽬录、写前端代码、设计API等。

2）每完成⼀步，系统会把结果反馈回去，LLM再判断下⼀步做什么，或者是否需要修正。这个过程就像不断⾃问⾃答：我做了什么？现在处于什么状态？接下来该⼲什么？

3）决策落地依赖外部⼯具⽀持。LLM本⾝不会写⽂件、调接⼝，但它可以输出结构化指令，由代理程序去执⾏shell命令、读写代码⽂件、调⽤搜索引擎或 API。像 LangChain 这类框架就提供了这类动作的封装。

4） ⾃主性是有边界的。它没法真正理解因果，只是根据上下⽂概率⽣成“合理”的下⼀步。⼀旦任务链偏离预期，容易陷⼊⽆限循环或重复操作。实际使⽤中经常需要⼈⼯⼲预⽌损。

整个流程本质上是⼀个带记忆的 ReAct 模式（Reasoning $^ +$ Acting），靠 prompt 把推理和动作绑定在⼀起。典型结构如下：

所以别被“⾃主”俩字唬住，它压根不经过真实逻辑判断，全靠模型“觉得下⼀步应该这么做”。复杂任务搞不定，⻓期运⾏稳不住，但做点⼩⾃动化脚本⽣成还能扛住。
